# Правила разработки Ficusin Store

Этот файл действует на весь репозиторий. Его обязаны соблюдать люди и ИИ-агенты.

## Источники истины

Разные источники отвечают на разные вопросы:

1. Явная задача владельца и её критерии приёмки — что изменить сейчас.
2. `docs/PRODUCT.md` — утверждённое целевое поведение бизнеса.
3. `docs/DECISIONS.md` — действующие архитектурные ограничения.
4. `docs/openapi.yaml` — текущий публичный HTTP-контракт.
5. Код и SQL-миграции — фактическое текущее поведение production.

Код нельзя выдавать за правильное целевое поведение только потому, что он уже написан. Документ нельзя выдавать за реализованную функцию, если её нет в коде. Любое расхождение нужно явно назвать и исправить код или документацию в том же PR либо записать как открытый долг.

## Архитектурные границы

- `frontend/` — React + TypeScript + Vite. Он не обращается к PostgreSQL и не содержит секретов.
- `backend/` — единственный Go API, бизнес-логика, БД и внешние интеграции.
- `timeweb/migrations/` — единственный способ изменять схему PostgreSQL.
- Новые HTTP-методы создаются только под `/api/v1` и сначала описываются в OpenAPI.
- Проверки во фронтенде нужны для удобства, но все бизнес-ограничения повторно выполняются в Go.
- Денежные значения внутри БД и бизнес-логики хранятся в минимальных единицах либо точном NUMERIC, не в float для новых расчётов.

## Бизнес-инварианты

- Гость может оформить розничный заказ.
- Телефон нормализуется к формату `+7XXXXXXXXXX`.
- Вход не создаёт клиента. Клиент создаётся только при регистрации после подтверждения номера.
- Серверная сессия хранится в HttpOnly-cookie и действует на всех страницах.
- Saby — внешний источник артикулов, базовых цен, остатков и складов.
- Локальная БД хранит рабочую копию каталога, клиентов, скидки, контент, заказы и настройки.
- Заказ всегда повторно проверяет цену, наличие и доступность товара на сервере.
- Сбой Telegram не отменяет сохранённый заказ: уведомление должно повторяться фоновым обработчиком.
- Оптовые ограничения нельзя считать реализованными, пока они не проверяются сервером и не покрыты тестами.

## База данных

- Никогда не редактировать уже применённую migration. Добавлять следующий нумерованный SQL-файл.
- Migration должна быть повторяемой там, где это возможно, и безопасной для существующих данных.
- Изменение таблиц сопровождается обновлением `docs/DATA_MODEL.md`.
- Удаление или массовое изменение данных требует отдельного подтверждения владельца.
- Не запускать миграции во время Docker build. Они применяются приложением при старте.

## Безопасность

- Не добавлять токены, пароли, сертификаты, приватные ключи и реальные строки подключения в Git.
- Названия переменных разрешены в документации; значения — только в Timeweb/GitHub Secrets или зашифрованном хранилище интеграций.
- Не писать секреты и персональные данные в логи.
- Новые административные методы требуют серверной проверки роли.
- Cookie production: HttpOnly, Secure, SameSite=Lax, Path=/.
- Любая интеграция с входящим webhook должна проверять подпись и быть идемпотентной.

## Рабочий процесс

1. Начать с актуального `main`.
2. Создать ветку `agent/<краткое-название>`.
3. Перед кодом зафиксировать критерии готовности.
4. Изменить код, тесты и связанную документацию.
5. Запустить обязательные проверки.
6. Открыть draft PR и дождаться зелёного CI.
7. Не сливать в `main` и не выкатывать production без явной команды владельца.

## Обязательные проверки

- Frontend: `npm ci`, `npm run lint`, `npm run build`.
- Backend: `go test ./...`, `go vet ./...`, `go build ./cmd/api`.
- Production: `docker build -t ficusin-store .`.
- Для новой бизнес-логики обязательны позитивный тест, тест отказа и тест граничного случая.
- После деплоя выполнять безопасную smoke-проверку health, публичных страниц и API без реальной оплаты или создания фиктивного заказа.

## Definition of Done

Задача готова, только если:

- критерии приёмки выполнены;
- проверки и CI зелёные;
- API и модель данных документированы;
- ошибки имеют понятные пользователю сообщения;
- нет секретов в diff;
- предусмотрены повторные запросы и частичные сбои интеграций;
- указано, что проверено автоматически, а что требует ручного бизнес-теста.
