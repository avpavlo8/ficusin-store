# Фикусин

Интернет-магазин растений с отдельными клиентским приложением и API.

```text
frontend/  React + TypeScript + Vite
backend/   Go HTTP API
timeweb/   SQL-миграции PostgreSQL
```

В production используется один контейнер: Go обслуживает `/api/v1/*` и
собранные Vite статические файлы. Это сохраняет один тариф Timeweb, но код,
зависимости и секреты frontend/backend полностью разделены.

## Локальный запуск

Требуются Node.js 24, Go 1.26 и PostgreSQL.
Frontend и backend запускаются в двух терминалах из корня репозитория.

```bash
# frontend, http://localhost:5173
cd frontend
npm ci
npm run dev

# backend, http://localhost:8080
cd backend
DATABASE_URL='postgresql://...' \
APP_ENV=development \
MIGRATIONS_DIR='../timeweb/migrations' \
AUTH_COOKIE_SECURE=false \
PROCUREMENT_PDF_FONT='/System/Library/Fonts/Supplemental/Arial.ttf' \
go run ./cmd/api
```

Vite проксирует запросы `/api` на Go по адресу `http://localhost:8080`.
Путь шрифта выше — пример для macOS. Для локальных PDF и Go-проверок укажите
существующий TTF через `PROCUREMENT_PDF_FONT`; на Linux выберите установленный
шрифт. Docker уже включает DejaVu и использует `/app/fonts/DejaVuSans.ttf`.

### Локальный просмотр интерфейса закупок

Для совместной проверки интерфейса без PostgreSQL и внешних интеграций:

```bash
cd frontend
npm ci
npm run dev -- --config vite.procurement-preview.config.mjs --port 5184
```

Откройте `http://127.0.0.1:5184/admin?section=procurement`.
Это реальный React-интерфейс с явно обозначенными демонстрационными данными.
Входы создания — загрузка инвойса/счёта и единое окно рекомендаций с составом.
Документы видны внутри закупки. На стенде PDF сохраняется в памяти; разбор строк
выполняет рабочий backend, что явно указано в карточке.
Массовый выбор рекомендаций работает без фильтра по поставщику, выбирая доступные
строки одного поставщика и пропуская остальные.
Черновики и поддержанные изменения хранятся в памяти локального сервера и
сбрасываются при его перезапуске. Неподдержанные внешние операции возвращают
понятную ошибку; запросов к production нет. Обычная сборка этот API не включает.

## Проверка

```bash
(cd frontend && npm test && npm run lint && npm run build)
(cd backend && PROCUREMENT_PDF_FONT='/System/Library/Fonts/Supplemental/Arial.ttf' go test ./... && go vet ./...)
(cd e2e && npm ci && npx playwright install && npm test)
docker build -t ficusin-store .
```

Архитектурные правила и порядок переноса описаны в
[`docs/split-architecture.md`](docs/split-architecture.md).

В репозитории нет второго серверного runtime: production-сборка и локальная
разработка используют один и тот же Go API и один React-клиент.

## Как разобраться в системе

В панели сотрудников есть [раздел «Инструкции»](docs/admin-instructions.md):
30 визуальных памяток по СБИС, WB, Ozon, сайту, Flowwow, Авито и СДЭК.
Изображения со стрелками можно увеличивать, скачивать и печатать;
схемы и реальные скриншоты обозначены отдельно.

Цены внешних площадок готовятся и подтверждаются в общем редакторе товара;
[описание публикации цен и восстановления заданий](docs/editor-price-publications.md).
Сохранение настроек площадок передаёт только поля API: исходный артикул из
интерфейса выбора связи остаётся в черновике редактора.
Ошибки проверки настроек редактора показывают причину отказа в форме.
Автоматические цены WB/Ozon проверяются тем же расчётом от цены сайта и упаковки,
который показан в редакторе; закупочная себестоимость относится к расчётам закупок.
Закупочные расчёты и предпросмотр цен с явными режимами `cost`/`retail`
описаны в [документации закупок](docs/procurement.md).
Продажи Ozon загружаются через FBS v4 и FBO v3 с курсорной пагинацией;
устаревшие методы списка отправлений больше не используются.
Фоновые закупочные задания используют сохранённые очереди PostgreSQL;
отдельного планировщика внешних продаж в памяти процесса нет.

Начните с [актуальной карты функций и процессов](docs/current-system.md),
затем прочитайте [правила работы с репозиторием](AGENTS.md).
Карта отделяет рабочие функции, переходную совместимость и исторические документы.
HTTP-контракт находится в [OpenAPI](docs/openapi.yaml).
Правила отправки отзывов после покупки описаны в
[документации отзывов](docs/plant-passports-and-reviews.md).
Оплата запускается через расчёт текущей задолженности заказа; прежние внутренние
`payment.Start`/`Sync` удалены. Редактирование карточки и фотографий из PDP ведёт
в общий редактор товара. Оставшиеся пути чтения исторических данных и условия
их снятия описаны в [границах совместимости](docs/remaining-compatibility.md).
Локально подготовлен [перенос оставшихся данных](docs/legacy-data-transition.md):
архивы с проверкой точности, V2-черновики с backup, отдельные артикулы площадок
и барьер нулевых резервов. Неперенесённые данные блокируют миграцию;
неизвестные внешние результаты не сбрасываются.
Оплата при получении использует [резерв сайта и СБИС](docs/cashier-stock-reservations.md):
в счёте указываются общий покупатель «Сайт Фикусин» и короткий комментарий
«Резерв заказа …». Обновление этих реквизитов сохраняет существующие строки и резерв.
физическое списание выполняет касса, вторую реализацию сайт не создаёт.
Нативный резерв в СБИС создаёт отдельный явно включаемый обработчик;
сам резерв не проводит счёт и не списывает физический остаток.
Полное покрытие последней проверки и сохранённые границы — в
[аудите всей кодовой базы](docs/whole-codebase-audit.md).

При окончательном отключении функции удаляются её код, настройки, фоновые
задания, устаревшие тесты и проверки, скрипты и ассеты; документация обновляется
в том же изменении. Правило и требования к сохранению данных закреплены в AGENTS.md.

Работы по очистке ведутся в отдельной ветке. Слияние в `main` запускает деплой
и автоматическое применение новых миграций; локальная проверка не означает,
что production уже обновлён.
### Flowwow

При создании передаются до 6 фотографий сайта с обложкой. При обновлении к
текущей галерее применяются изменения сайта с сохранением фото из кабинета.
Логические свойства Seller API нормализуются из `0/1`.

Отдельный раздел панели и канал общего редактора: создание/привязка карточек,
отправка названия, описания, фото и цены сайта, автоматическое обновление цен и
остатков. Ключи backend: `FLOWWOW_API_TOKEN`, `FLOWWOW_SHOP_ID`; реальные записи
подчиняются существующему production/live ограничению публикаций. Без ключей
сохраняются подготовки, без внешней отправки. Настройка, протокол и ограничения:
[docs/flowwow.md](docs/flowwow.md).

Проверка отсутствия реализации СБИС учитывает ответ JSON-RPC «документ не найден» с HTTP 500; повтор до первой записи использует тот же UUID без создания нового задания.

Начальная цена карточки и подтверждённая публикация цены СБИС обновляют как
основную «Цену», так и настроенный прайс; завершение подтверждается чтением обеих
проекций. Редактирование контента существующего товара сохраняет цены.
Регламент новой реализации выбирается по публичному UUID. После подтверждения
создания повторяется только чтение нативной привязки; несовпадение числового
регламента блокирует проведение и показывает точную причину.
Полный редактор карточек, включая цены, варианты, фотографии и связи со СБИС, Ozon и Wildberries, доступен владельцу, администратору и менеджеру. Новые загрузки сохраняют ориентацию снимков. Для связанных карточек редактор применяет добавления и удаления сайта к текущей галерее площадки.

Владелец, администратор и менеджер могут удалить отдельную карточку из строки каталога (право `products.manage`). Свободный черновик удаляется; опубликованная карточка или черновик с остатками, заказами, внешними связями либо историей сохраняются в архиве. Архив исключён из активного списка, фотографии и ссылки заказов остаются. Внешние карточки СБИС и маркетплейсов не удаляются. Во время сохранения редактор блокирует поля, переключатели и изменение фотографий; при ошибке снова разрешает редактирование. Связи Авито, снимки синхронизации Flowwow и история перепривязок сохраняются при одиночном и массовом удалении. Явное успешное сохранение полностью завершает все шаги редактора, закрывает его и показывает результат и предупреждения обмена в каталоге; ошибка оставляет редактор и черновик открытыми.

Незавершённые старые создания СБИС также проверяют основную цену. Её отдельное
исправление не повторяет Create или сохранённый контентный Update.

Ошибочный ID регламента пустого подтверждённого черновика может явно согласовать
владелец через внутренний сервис: исходные запросы сохраняются, исправление и
readback записываются неизменно, новая реализация не создаётся. Подробности —
[docs/saby-order-realizations.md](docs/saby-order-realizations.md).

Временное состояние проводок после `PostAsync` проверяется ограниченным числом
чтений; автоматического повторного проведения нет.

Подтверждение удаления карточки каталога открывается общим модальным окном по центру
экрана. Escape, крестик и «Отмена» закрывают его без удаления; на время запроса
закрытие заблокировано. Текст результата и правила удаления/архивирования сохранены.
