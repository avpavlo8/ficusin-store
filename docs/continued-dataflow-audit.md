# Повторный аудит потоков данных, схемы и тестов

Дополнительный проход 14 ноября 2026 после [полного аудита](whole-codebase-audit.md).
Проверка ищет значения, которые только записываются, устаревшие обходные пути
и тесты, которые не проверяют заявленное поведение. Рабочие функции и их
границы описаны в [current-system.md](current-system.md).

## Удалённые остатки

| Область | Изменение и доказательство |
|---|---|
| Клиенты | Удалены `ListCustomers` и HTTP-fallback непостраничного хранилища. Единственный production repository поддерживает `ListCustomersPage`; интерфейс теперь требует его явно. |
| Возврат обновлённого клиента | `UpdateCustomer` читает конкретный ID через общую со списком SQL-проекцию. Прежде после commit он просматривал первые 100 клиентов и возвращал ошибку для более старой записи. Роли, скидки, счётчик заказов и аудит сохранены. |
| Подборки | `ListForCollection` входит в обязательный контракт каталога. Удалены две проверки «хранилище ещё не поддерживает подборки» из handler/cache. Фильтрация SKU, отдельный cache key и настоящий `ErrNotFound` сохранены. |
| Кабинет | `ListPageForCustomer` обязателен в HTTP-контракте; partial-pager fallback снят. URL без `view` и его прежняя форма ответа остаются действующим контрактом, а не объявляются лишними по одному отсутствию нового UI-вызова. |
| СБИС | Приватный `sabyDraftPayload` читает только необходимые поля идентичности/состава. Удалены нечитавшиеся order number, supplier metadata, line code/price/cost. Он используется только для декодирования, не для повторной сериализации. Исходный `item.Payload`, замороженные расходы и read-only recovery не меняются. |
| Привязка карточки СБИС | Удалён нечитавшийся `mirrorFound` из SQL-проекции, Go/TS DTO, OpenAPI и фикстур. Само зеркало, ID/code, папка, категория, aliases и разграничение readonly links/сохранённого плана остаются. |
| Другие декодеры | Удалены нечитавшиеся create-response `CDEK.Requests.State`, `WB.cursor.Total`, `Ozon.errors.Code`, `YooKassa.failure.Parameter`. Декодеры допускают дополнительные поля. Используемый CDEK tracking state и сообщения ошибок сохранены. |
| Чат | Удалён DOM-ref кнопки закрытия `QuickChat`, который только присваивался. Управление фокусом через panel, обработчик закрытия и возврат к launcher остаются. |
| Загрузка кабинета | Сняты три отдельных пути создания шапки для loading/error/готового профиля. Единый main/`StoreHeader` сохраняет поиск и фокус; `AccountShell` отвечает только за прежнюю внутреннюю секцию. Готовая DOM-разметка и права не меняются. |
| Диагностика СБИС | Удалены workflow input `receipt_guid`, переменная `SABY_RECEIPT_GUID` и её неиспользуемая валидация. Оба read-only RPC используют числовой ID; его положительность проверяется до сети. |
| Генератор контента | Удалён неиспользуемый Python import. Воспроизведение исторического SQL не изменилось. |
| Старая аналитическая сводка | Удалены 11 нечитавшихся полей `Summary`, `daily.sessions`, четыре типа строк, шесть запросов веб-воронки и traffic CTE дневного ряда. Оба нынешних UI читают финансовые агрегаты `sales_events`; продажи/возвраты/каналы/качество привязок сохраняются. Активный журнал событий, атрибуция и Метрика не сняты. |
| Характеристики PDP | Оба пути карточки и основные факты используют актуальные `displayValue`/`optionLabels`. Раньше произвольный enum PIM показывался внутренним кодом. Подтверждены падающие до исправления примеры растений и кашпо; текущий metadata-free fallback остаётся. |

Наличие поля в JSON провайдера не означает, что приложение должно хранить
для него отдельное поле Go. Обратное правило тоже важно: DTO, который затем
сериализуется или хранится как frozen payload, нельзя сокращать по отсутствию
прямого чтения одного поля.

## Проверки, которые действительно проверяют поведение

- Удалён source-presence guard закупочных тележек: он искал текст вызова в Go
  и проходил бы даже с этим вызовом в комментарии. Новый PostgreSQL-сценарий
  вызывает `OrderDetail`, проверяет восстановление `shelf`/пустого номера в `1`,
  сохранение ручного `7`, два физических номера в валидации и commit трёх строк.
  При отключении рабочего вызова через Go overlay тест падает на оставшемся
  `shelf`. Изменений runtime ради нового теста нет.
- Регрессия изменения клиента создаёт 201 запись. Целевой клиент отсутствует
  на первой странице, но после изменения возвращаются его ID, роль, скидка,
  сумма покупок и количество заказов. Отдельно проверены права, аудит и запрет
  отключения собственного аккаунта.
- Удалён CRM fixture `ficusin:procurement-plan-draft:v1`: тест сам записывал
  нечитавшийся ключ localStorage и сравнивал его с собой. Текущие проверки
  серверных личных/общих черновиков в browser/PG сохранены.
- Удалены проверки снятых AI/export-путей и ставший write-only массив
  `fixture.calls`. Проверка редактора СБИС усилена: до Save нет никаких записей,
  после Save выполняется ровно один текущий `PUT editor-plan` с точным ID.
- Удалён отдельный тест трёх снятых delivery API: он проверял только обычный
  router 404. Текущие доставка, изоляция неизвестных API и проверка прав остаются.
- Удалены дублирующий вызов другого PG-теста, проверки девяти снятых catalog API,
  runtime type assertion, повторявший compile-time гарантию, и строковая проверка
  popularity SQL, уже покрытая реальными продажами/отменами/неоплатой на PG.
- Два других source guard заменены настоящими PG-сценариями: стабильные option ID,
  деактивация/возврат вариантов и сохранение выбранных значений; 13 вариантов
  автоотмены с оплатой, предзаказом, уведомлением, остатком и отказом провайдера.
  Контролируемые no-op мутации оставляли прежние проверки зелёными, новые
  сценарии падали. Пустые текстовые дубли Python сняты; источники миграций
  и оставшиеся ограниченные static contracts явно отделены от поведения.
- Реальное выполнение ранее пропускавшегося теста отменённой отправки выявило
  невалидную фикстуру без обязательной стоимости доставки. Теперь она содержит
  собственный SKU, свежий остаток и позиции отправки. Положительный контроль
  создаёт один локальный платёж у fake provider; после отмены обе защиты
  возвращают конкретную ошибку, не создают платежей и не меняют остатки.
  Два независимых отключения защит через overlay ломают тест; платёжный runtime
  для исправления фикстуры не менялся.
- Полный browser run выявил один нестабильный autocomplete case. Причина
  воспроизведена управляемой задержкой `/auth/me`: смена loading-shell на
  `AccountShell` удаляла input с введённым запросом. Новый тест падает до
  исправления и проверяет фокус, запрос, подсказки и переход ко всей выдаче
  после ответа. Стабильная шапка устраняет причину; 149 выбранных cases прошли
  без retries. Timeout/retry настройки и исходный тест не ослаблялись.

Новые PG-регрессии включаются в CI с настоящим подключением к тестовой БД;
успешный unit-run без переменной окружения не считается их выполнением.

## Дополнительная проверка всей базы

Схема 220 содержит 1 246 колонок `public`. Низкое число текстовых упоминаний
проверяется вместе с функциями, триггерами, представлениями, сериализацией и
фоновыми процессами. Например, `catalog_editor_link_history` заполняется
триггером, а `sales_sync_state` и `wb_sync_state` обслуживают действующие workers.
Они не удаляются по отсутствию прямого имени таблицы в Go.

Анализ качества тестов охватывает 745 Go test-функций в 279 файлах до удаления
дублирующего wrapper. Исполняемая проверка результата отличается от простого
вызова другого теста, self-comparison и наличия строки в исходнике. Исторические
источники контента/миграций отдельно проверяют воспроизводимость; возраст файла
не делает такую проверку пустой.

Финальный inventory: 742 Go test-функции, 280 `*_test.go` с учётом helpers;
159 DB-проверок. Найдены 15 случаев, которым CI не передавал нужное окружение
либо не выбирал их имя. Исправлены обе workflow: Verify и CRM acceptance;
изолированным публикациям/workflow выделена требуемая локальная БД. Теперь
159/159 имеют selector и окружение; это статическая достижимость, которую
необходимо подтвердить исполнением. Два слабых Python case удалены: 41/41.
Один PG-case группировки инвойса был выбран двумя шагами одной CRM-базы;
дублирующий запуск снят. Повторная сверка сохранила все 159 достижимых cases.

Полный срез схемы 220: 110 таблиц, одно представление, 1 246 колонок. Все 108
колонок с редкими ссылками в 45 relations проверены по реальным consumers.
Подтверждённый неиспользуемый остаток — `orders.organization_id`: нет текущих
writers/readers, триггеров и JSON-снимков, использующих прямую связь. Миграция
221 сохраняет все исходные строки, включая NULL и `created_at`, в независимой
`legacy_archive.order_retired_organization_links` и удаляет колонку без CASCADE.
Организации и членство остаются. Проверены точный архив, неизменность остальных
данных заказа/членства, пустая установка, новые записи и атомарный отказ при
неожиданном зависимом view. После миграции в `public` остаются 1 245 колонок.

Срез frontend/API охватывает все 177 файлов, 189 typed response boundaries,
3 017 определений полей, 149 структурных переходов, 138 мест сериализации и
69 прямых query readers. Среди 167 статических no-read кандидатов отдельно
подтверждены удалённые `daily.sessions`/`mirrorFound` и исправлены потребители
PIM-подписей; остальные не удаляются массово. Общий ответ API, generic/spread,
параметр провайдера или сохранённый снимок требуют проверки backend и полного
пути данных. Отсутствие ссылки на конкретный TS-symbol не доказывает снятие
функции. Активный fallback старых карточек имеет текущих потребителей.

Production-данные и внешние операции не менялись. Сохранённые bytea, прежние
публичные медиа, неизвестные результаты внешних записей и aliases имеют
описанных consumers. Для 11 неподтверждённых публичных изображений по-прежнему
нет достаточной проверки production URL; они остаются до такой проверки.

## Проверка результата

Локально прошли Go test/vet/build, OpenAPI 236/91, frontend build/lint/format/budget,
82 frontend unit и 41 Python. На свежей схеме 221 и настоящем окончательном API
прошёл CRM для owner/manager в 1440/390 px с сохранением галереи. После исправления
PIM прошли 119 широких и 19 финальных browser cases; это выбранные проверки,
а не заявление о полном браузерном прогоне. Ранее пропущенные 15 PG-сценариев
выполнены на подходящих изолированных БД; пять новых регрессий схемы/данных
также прошли. Контролируемые мутации тележек, options, автоотмены и защиты
платежа падали, обычные сценарии оставались зелёными.

Для окончательного runtime `5ab8af80f0655a4fa76c65d2007c93e8df8a9915`
успешно завершены
[Verify 43580879335](https://github.com/avpavlo8/ficusin-store/actions/runs/43580879335)
и [CRM acceptance 43580882002](https://github.com/avpavlo8/ficusin-store/actions/runs/43580882002).
Все 895 browser executions прошли сразу: 448 + 447, без skip/flaky/retry.
Обычный autocomplete и управляемый authGate входят в этот прогон. Frontend
82/82, Python 41/41, backend test/vet/build, OpenAPI, все 221 миграция и
PG gates, Docker build/boot/tools/commerce/load/backup-restore прошли.
CRM workflow исполнила настоящий API/UI, возвраты и чат; единственный
invoice-group case больше не запускается дважды. Условный dependency-review
предназначен для PR и при manual dispatch не запускался.

Предыдущий полный run выявил race шапки и не считается окончательным
результатом: после исправления выполнен новый полный прогон. Финальный коммит
документации не меняет проверенный runtime. Production deploy не выполнялся.
