Для любого конкретного запуска обязательна транзакционная проверка `products.id` ↔ `product_code`, одинакового латинского вида/сорта, всех SKU и X-кодов `saby_nomenclature`, отличимых размеров, категории, различий описания и ухода, существующих отзывов/заказов, внешних ID и всех FK на `products`. Разные значимые значения блокируют объединение; их необходимо разрешить вручную. Исторические заказы и отзывы сохраняют свои ID и SKU, старые числовые URL получают алиасы, а фото и связи маркетплейсов переносятся со SKU.

Дополнительные блокеры после ревизии: нельзя потерять заполненные поля `plant_kind`, свет, полив, класс высоты, сложность ухода, размещение, безопасность для животных и форму роста. Пустые значения переносятся с исходной карточки, разные непустые значения останавливают операцию. Внешние ID исходной карточки с одним SKU привязываются к этому SKU одновременно со сменой `product_id`; при нескольких SKU и неразобранных ID объединение запрещено. Ручная синхронизация всей объединённой карточки с СБИС запрещена: у размеров разные Saby ID, поэтому её прежний источник `products.saby_id` недостоверен для всей карточки.

Внешние ID с одним SKU обновляют `product_id` и `variant_id` одним SQL-запросом: ограничение `product_external_ids_variant_owner` проверяет их соответствие после каждой операции. Проверка этого ограничения на тестовой копии БД остаётся обязательной до выпуска.

Путь выпуска: сначала прогнать проверку на копии production DB, затем проверить страницы старых URL и каждую связку СБИС/маркетплейса, после этого выполнять отдельные подтверждённые группы. Текущий код намеренно не может слить карточки с пустым/разным латинским названием или без X-кода хотя бы одного SKU.

Ручное подтверждение таксона: владелец проверяет обе позиции в СБИС, сорт по фотографиям и закупочным документам, выбирает единое принятое латинское название с видом либо именованным сортом, затем обновляет `latinName` на каждой карточке через существующее редактирование товара. Это изменение попадает в аудит карточки. После сверки всех SKU/X-кодов запускается транзакционный preflight merge. Название только из рода (`Ficus`, `Zamioculcas`, `Dypsis`) теперь блокирует merge даже при точном совпадении строк. Синонимы (`Dypsis`/`Chrysalidocarpus`, `Sansevieria`/`Dracaena`) не уравниваются алгоритмом: владелец сначала подтверждает фактический вид и вручную приводит обе карточки к одному каноническому Latin. Отдельный endpoint подтверждения таксона с источником доказательства полезен в следующем этапе, но текущее API уже поддерживает исправление `latinName` и аудит.

После выпуска read-only проверка доступна владельцу в админке: «Товары» → выбрать опубликованные растения одной группы → «Проверить объединение». Диалог показывает внутренние ID и публичные адреса; нужно указать основную карточку, сверить **все** SKU и нажать «Проверить без изменений». Сервер выполняет ту же проверку в транзакции PostgreSQL `READ ONLY`; фактический merge повторяет её под блокировками. [Шаблон восьми групп](catalog-merge-eight-preview-template-2026-10-12.json) содержит публичные коды и ожидаемые SKU из снимка, но внутренние `products.id` оставлены пустыми намеренно: их следует взять из свежей админки после релиза. Шаблон нельзя отправить в API до такой сверки.
