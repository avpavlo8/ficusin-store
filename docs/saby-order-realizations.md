# Реализации заказов в СБИС

При включённом обработчике реализация создаётся сразу после оформления
любого нового заказа, включая неоплаченный и самовывоз с оплатой при выдаче.
Передача СДЭК и завершение заказа второй документ не создают. Старые заказы
автоматически в этот режим не переводятся; для них остаётся явная подготовка
по прежнему событию передачи.

Отмена заказа до физической передачи сохраняет желаемое состояние в той же
транзакции и запускает обратный обмен. До первого внешнего запроса задание
можно остановить без документа. Уже проведённый собственный документ снимается
с проведения одним `Документ.CancelPosting`; результат подтверждается чтением.
Если создание или проведение было в полёте, сначала разрешается его результат.
Неизвестный POST не повторяется. После физической передачи автоматическая
компенсация блокируется до проверки возврата товара.

При зарегистрированной или неизвестной заявке СДЭК обратное списание ждёт
подтверждённой отмены у перевозчика. Подтверждённый локальный `CREATED` не
доказывает отсутствие физической передачи. Для частичных оплаченных отправок
без подтверждения отмены остаётся ручная сверка. Событие перевозчика и отмена
используют общий порядок блокировок: родительский заказ, блокировка обмена,
затем отправка. Последняя проверка автоотмены заново читает оплату под
блокировкой, поэтому подтвердившийся за время запроса платёж сохраняет заказ.

Автоотмена доступной брошенной онлайн-оплаты использует существующую настройку
`orders.auto_cancel_hours` (по умолчанию 24 часа, 0 отключает). Самовывоз с
оплатой при выдаче и заказы в ожидании менеджера так не отменяются.

## Исполнение

В транзакции со статусом заказа сохраняется событие. Отдельный обработчик
создаёт обычную «Реализацию», связывает настроенного покупателя, заполняет
точные товары и цены, проводит документ и проверяет результат чтением.
«Реализация розницы» кассовой смены для этого процесса не используется.
Оплата, фискализация, электронная подпись и отправка контрагенту не вызываются.

Проверенные методы:

- `СБИС.ЗаписатьДокумент`, protocol 3: обычная операция «Реализация» и заранее
  сохранённый UUID операции. Этот UUID является публичным идентификатором ЭДО.
- `ДокОтгрИсх.СписокХраним` и `ДокОтгрИсх.Прочитать`: получение отдельного
  числового ID и нативного UUID с обязательной сверкой публичного UUID.
- `РеалИсх.Записать`, protocol 7: минимальная запись существующего ID и покупателя.
- `РеалИсх.DocNomCreate` и `РеалИсх.CustomDocNomUpdate`, protocol 7:
  подготовка полной типизированной строки и её единственное сохранение.
- `Документ.PostAsync`, protocol 7: складское проведение.
- `ДокОтгрИсх.Прочитать` и `РеалИсх.DocNomList`: независимое подтверждение.

Пустой ответ `PostAsync` допустим и сам по себе не подтверждает списание.
Успех требует `Проведен=true`, `ЕстьПроводки=true`, отсутствия ошибок,
неактуальных проводок и обеих очередей. Все расходные строки должны быть
закрыты и совпадать с сохранённым заказом по документу, складу, числовому ID
номенклатуры, количеству, цене и сумме. ID склада заголовка и движения
сохраняются отдельно: равенство между ними не предполагается.

Перед изменением фиксируется этап и полное подтверждение запроса. Записи не
повторяются автоматически после тайм-аута, 401, перенаправления, перезапуска
или неясного ответа. Для известного документа выполняется только чтение;
потерянный ответ создания без нативной привязки требует ручной сверки.
Исчерпание ограниченных проверок переводит задание в «Требует проверки».
Один внешний документ не может подтвердить две разные передачи.

## Настройки и STG

По умолчанию `ORDER_REALIZATION_MODE=disabled`. Рабочий `live` разрешён только
при `APP_ENV=production`, `ORDER_REALIZATION_LIVE_ENABLED=true`, настроенном
СБИС и явно проверенных ID: локального склада, нативного склада, склада
движений, организации, операции и покупателя. Покупатель задаётся через
`ORDER_REALIZATION_BUYER_ID`; тестовый покупатель в код не зашит.

На STG используется `ORDER_REALIZATION_MODE=mock` с отдельной базой. Весь
внутренний цикл выполняется, но реальные документы и остатки не меняются.
Результат явно помечен тестовым, ID начинается с `STG-SALE-`. Переключение
режима не превращает прежнее тестовое задание в рабочее. См. [staging.md](staging.md).

## Проверка настоящего API 13 ноября 2026

Создана обычная тестовая реализация `FCT-20261113-1` (нативный ID `42807`).
В ней одна отдельная тестовая номенклатура `X380416519` / ID `3899`, количество
1, цена 1 ₽. Проведение выполнено одним вызовом `Документ.PostAsync`.
Независимое чтение подтвердило проводки без ошибок/очереди и закрытую
расходную строку `175645`. В карточке СБИС остаток изменился с 1 на 0.
Клиентские заказы, оплата и касса в этой проверке не использовались.

Проверки API выполнялись отдельными диагностическими заданиями, без изменения
production-приложения или его окружения:
[привязка покупателя](https://github.com/avpavlo8/ficusin-store/actions/runs/43480175718),
[единственный запрос проведения](https://github.com/avpavlo8/ficusin-store/actions/runs/43480461980),
[подтверждающее чтение](https://github.com/avpavlo8/ficusin-store/actions/runs/43480685110).
У задания отправки статус failure: его немедленный проверочный запрос
остановился на промежуточном складском состоянии. Повторного проведения не
было; последующее отдельное чтение подтвердило завершение.

На том же собственном тестовом документе проверена обратная операция:
`Документ.CancelPosting`, protocol 7, с типизированной записью `docRec`,
содержащей только `@Документ`, и `eventRec=null`. Ответ содержит
`operationResult=true`; интерфейс показал снятое проведение, а свежий поиск
номенклатуры `X380416519` в каталоге — восстановленный остаток 1 шт. Этот
запрос не удаляет документ и не отменяет оплату. Повторного проведения не было.

Автоматическая отмена сохраняет отдельное подтверждение, не стирая исходный
документ и доказательство списания. Цена и состав запроса неизменяемы. Пока
отдельный протокол корректировки не реализован, изменение состава, цен и
скидки раннего заказа отклоняется; неизменённая форма не пересоздаёт строки.

Отдельная проба без сохранения проверила цену из фильтра `DocNomCreate`:
запрошено 1,01 ₽, подготовленная цена и сумма — 1,01 ₽, ID строки отсутствует,
сохранённая строка и проведение не изменились.
[Подтверждение подготовки цены](https://github.com/avpavlo8/ficusin-store/actions/runs/43487816599).
[Чтение после отмены](https://github.com/avpavlo8/ficusin-store/actions/runs/43486159991)
подтвердило снятое проведение и ту же незакрытую строку; остаток в каталоге
вернулся с 0 на 1.

## Доступность и импорт остатков

`order_sale_inventory` исключает ещё не отражённые ранние удержания из
свободного остатка. `order_sale_owned_quantity` даёт кредит только своему
заказу с учётом очередности: поздний предзаказ не отнимает последнее растение
у первого заказа. Подтверждённая реализация учитывается при оплате, сборке и
отправке своего заказа, даже если импорт СБИС уже показывает ноль.

Источник передаёт `stockObservedAt` — начало сбора до первого GET СБИС,
а не время загрузки в сайт. Только снимок, начатый после подтверждённого
списания, освобождает его локальное удержание. Запоздавший или неизвестный
снимок не воскрешает проданную последнюю единицу; старый именованный снимок
также не перезаписывает более новый остаток. Для mock удержание действует
до подтверждённой тестовой отмены, поскольку внешнего движения не было.
