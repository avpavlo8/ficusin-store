# Журнал решений

Запись считается принятой, пока новая запись явно её не заменит.

| ID | Решение | Причина | Последствие |
|---|---|---|---|
| ADR-001 | Frontend: React + TypeScript + Vite | Простой SPA без второго server runtime | Бизнес-логики и секретов во frontend нет |
| ADR-002 | Backend: Go | Владелец знает Go; нужен долгоживущий backend для магазина и склада | Все новые API и workers пишутся на Go |
| ADR-003 | PostgreSQL — основная БД | Нужны транзакции, связи, пользователи, заказы и склады | Схема меняется migrations |
| ADR-004 | Один production container на старте | Экономия тарифа Timeweb | Go отдаёт API и static; границы кода остаются раздельными |
| ADR-005 | GitHub `main` — production source | Автоматический и воспроизводимый deploy | Merge только после CI и команды владельца |
| ADR-006 | Saby — источник артикулов, базовых цен и остатков | Эти данные уже ведутся в учётной системе | Сайт хранит snapshot и не должен самовольно расходиться с Saby |
| ADR-007 | Телефон подтверждается звонком SMS.ru | Вход без пароля и SMS sender registration | Login и registration должны оставаться разными flow |
| ADR-008 | Server sessions в HttpOnly-cookie | Авторизация между страницами и меньше риск утечки token из JS | В БД хранится только token hash |
| ADR-009 | Сбой Telegram не откатывает заказ | Заказ важнее уведомления | После commit работает retry worker |
| ADR-010 | СДЭК пересчитывается на backend | Клиентским данным нельзя доверять | Заказ блокируется при неверном тарифе/ПВЗ |
| ADR-011 | YooKassa отложена | Нет готового payment lifecycle и webhook | Статус заказа пока `payment_provider_pending` |
| ADR-012 | Отдельный постоянный staging пока не оплачивается | На текущем этапе это лишние 510–810 ₽/мес | Изменения проверяются в ветке и CI; решение пересмотреть при росте команды/риска |

## Как добавлять решение

Новая запись должна содержать контекст, выбранный вариант, отвергнутые альтернативы, последствия и план миграции. Старые решения не удаляются — новая ADR указывает, какую запись заменяет.
