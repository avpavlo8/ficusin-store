# AI-подготовка товарной карточки

AI работает только в админке и никогда не публикует результат самостоятельно. Перед генерацией импортированные размеры объединяются в одну PRODUCT-карточку с несколькими SKU.

Редактор предлагает четыре независимых действия: сгенерировать описание, атрибуты, инструкцию по уходу или обложку. Текстовые действия отправляют исходное название, код СБИС и разрешённую категорийную схему на backend. Каждое запрашивает у Responses API только нужную часть JSON Schema с низким reasoning effort. Web search не запускается в интерактивном редакторе: он заметно замедлял запрос и создавал ложное ощущение, что единичный поиск гарантирует истинность карточки.

Ответ сразу заполняет соответствующие поля несохранённой формы. Отдельного окна принятия AI-предложения нет. Менеджер проверяет поля и нажимает «Сохранить» либо закрывает карточку без сохранения.

Обложка генерируется отдельной кнопкой после проверки сорта. Её арт-дирекция зафиксирована кодом: одно ботанически точное растение целиком, простое светлое кашпо, бесшовный тёплый кремовый фон, мягкий дневной свет и естественная тень; без интерьера, текста и декора. Image API возвращает WebP, backend кладёт его в своё S3 и назначает главным медиа PRODUCT. Реальные фотографии конкретных SKU остаются в галерее вариантов.

Секреты хранятся только в окружении: `OPENAI_API_KEY`. Пустой ключ отключает AI с HTTP 503, не влияя на каталог, импорт или редактирование вручную. Модель текста задаётся `OPENAI_TEXT_MODEL`.

Ограничения: быстрый режим опирается на знания модели и может ошибаться в сорте и ботанических свойствах. Токсичность, условия ухода и точные характеристики нельзя принимать только по уверенной формулировке модели. Для массового наполнения нужен отдельный фоновый research-процесс с источниками и очередью, а не блокирующий запрос из редактора.
