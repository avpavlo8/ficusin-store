# Атрибутно-категорийная модель каталога

## Контракт

- `attribute_definitions` хранит единственное определение атрибута: стабильный `code`, тип, аудиторию (`customer`/`technical`) и уровень значения (`product`/`variant`).
- `attribute_options` — единственный справочник вариантов `enum` и `multi_enum`; в JSON-значениях хранится `code`, а не подпись.
- `category_attributes` назначает атрибут категории. Ближайшее назначение в дереве перекрывает родителя; `is_excluded` явно отменяет наследование.
- `product_attribute_values` и `variant_attribute_values` разделяют свойства PRODUCT и SKU. Значение нельзя сохранить вне эффективной схемы категории или с неверным JSON-типом/enum-code.
- обязательность проверяется при публикации PRODUCT и активации SKU. Архивные исторические данные не ломаются при ужесточении схемы.
- `catalog_filters` ссылается на определение по ID; динамические подборки используют стабильный `code` в JSON-правиле.

## Публичная локализация

API не заменяет `value` русским текстом. Покупательский атрибут дополнительно возвращает `displayValue`, `options: string[]` и `optionLabels: Record<string,string>`. Labels читаются только из `attribute_options`; boolean отображается как «Есть»/«Нет». Для `multi_enum` `displayValue` содержит label каждого элемента. Неизвестный старый code безопасно возвращается без изменений.

```json
{"code":"pot_type","value":"self_watering","displayValue":"С автополивом","options":["cachepot","self_watering"],"optionLabels":{"cachepot":"Кашпо","self_watering":"С автополивом"}}
```

## Безопасное изменение схемы

1. Новое смысловое поле создаётся новым атрибутом.
2. Атрибут назначается нужной ветке категорий и проверяется как необязательный.
3. Значения переносятся и проверяются на витрине/в фильтрах.
4. После заполнения поле можно сделать обязательным.
5. Старое определение архивируется, но не удаляется из истории.

Обновление справочника выполняется upsert. Пропущенная опция деактивируется, но не удаляется: заполненные PRODUCT/SKU values сохраняются. Backfill требует предварительного `COUNT(*)`, резервной копии и отдельного обоснования; этап 1 backfill не выполняет.

Backend запрещает менять тип или scope атрибута, если значения уже существуют. Переименование `code` запрещено, пока его использует динамическая подборка. Это защищает каталог от тихого исчезновения товаров из правил.

## Ошибки, которые должен видеть оператор

- неизвестный/технический атрибут нельзя вывести на витрину;
- числовому атрибуту разрешён только фильтр-диапазон, нечисловому — список или чипы;
- исключённый атрибут нельзя одновременно сделать обязательным или отображаемым;
- PRODUCT/SKU нельзя активировать без обязательных значений;
- enum принимает только активный `code` из справочника;
- проданный SKU можно архивировать, но нельзя удалить.

## Честный аудит

Сильная сторона решения — нормализованные определения, раздельные PRODUCT/SKU-значения и вычисляемое наследование: нет копирования всей схемы в каждую категорию. Сервер, а не только React-форма, валидирует типы и обязательность. Фильтры и подборки используют ту же модель.

Компромиссы и ограничения:

- правила подборок хранят ссылки на атрибут по строковому `code`, поэтому переименование требует явного переноса правил; теперь опасное переименование блокируется;
- изменение набора enum-вариантов требует дисциплины: использованный вариант лучше деактивировать, а не удалять, иначе старое значение остаётся историческим, но не пройдёт повторное сохранение;
- обязательность применяется при следующем сохранении/публикации, а не массово выключает уже опубликованный каталог — это намеренная защита production;
- UI PIM функционален, но плотный: при сотнях атрибутов понадобятся поиск, группировка и отдельный отчёт полноты данных;
- миграции 055–060 сложны из-за совместимости со старым каталогом. После стабилизации полезно вынести compatibility-поля в отдельный план удаления, а не расширять их дальше.

## Проверки

- backend unit tests проверяют определения, фильтры, правила подборок и запрет опасной смены типа/scope/code;
- PostgreSQL migration gate применяет всю историю миграций и проверяет целостность PRODUCT/SKU;
- production-image test поднимает реальный контейнер и читает каталог;
- Playwright проверяет PIM, наследование схемы, варианты, фильтры и динамические подборки на desktop/mobile.
