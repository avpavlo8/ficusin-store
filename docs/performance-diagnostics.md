# Диагностика производительности production

## Что измеряем

Один `curl` не является замером. Для каждого URL делаются пять запросов в
одном процессе `curl`: первый включает создание TLS-соединения, следующие
используют keep-alive. Записываются `time_namelookup`, `time_connect`,
`time_appconnect`, `time_starttransfer`, `time_total`, HTTP-код и размер.

```bash
curl -sS --compressed -o /dev/null \
  -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} bytes=%{size_download} code=%{http_code}\n' \
  https://www.ficusin.ru/api/v1/health
```

Из управляемой среды запрос идёт через egress-прокси: `tcp` и DNS относятся к
нему, а не к origin. Поэтому инфраструктурную составляющую доказываем также
сравнением статического файла, простого `/health` и `Server-Timing` API.

## Внутренние метрики

Каждый HTTP-запрос получает случайный `X-Request-ID`. Структурный лог `http
request` содержит только безопасные агрегаты:

- `route`, `method`, `status`, `request_id`;
- `duration_ms` и `ttfb_ms` внутри приложения;
- `sql_queries` и суммарный `sql_ms`;
- `response_write_ms` и фактически отправленные `response_bytes`.

SQL, параметры, query string, cookies, токены и тела запросов не логируются.
Раз в минуту лог `postgres pool` показывает число занятых/свободных соединений,
`empty_acquires`, накопленное ожидание свободного соединения и отменённые
ожидания. Рост `empty_acquires` вместе с `empty_acquire_wait_ms` означает, что
десяти соединений пула не хватает; менять размер без этого сигнала нельзя.

У публичных JSON-ответов заголовок `Server-Timing` отдельно показывает время
загрузки данных и JSON-кодирования на cache miss. `X-Ficusin-Cache` принимает
значения `MISS` и `HIT`.

## Кэш и актуальность

`catalog`, `categories` и `collections` хранят уже сериализованный JSON до 15
секунд. Одновременный cache miss объединяется через singleflight. Браузерный
`max-age` равен 5 секундам; ETag даёт `304` без повторной передачи 500+ КБ JSON.

После успешного изменения кэш и короткий кэш PDP очищаются для маршрутов,
которые меняют товары, варианты, остаток, цену, категории, атрибуты, фильтры,
подборки, отзывы, заказы или синхронизируют каталог СБИС. Неуспешный запрос кэш
не сбрасывает. Фоновые изменения, которые проходят мимо HTTP API, ограничены
серверным TTL 15 секунд.

## PostgreSQL

CI после всех production-миграций выполняет оба фактических запроса через
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` и печатает планы:

- полный публичный каталог;
- восемь рекомендаций PDP.

План проверяется на живой PostgreSQL 16. Индексы не добавляются по строковому
совпадению в исходнике: новый индекс допустим только после плана production с
дорогим scan/sort и подтверждения, что существующие индексы его не покрывают.

## Baseline 24.08.2026

Контейнер: `02cf699ecbb9e1dc` (main после PR #254). Значения — первый запрос и

0,8–1,0 секунды. Это разделяет внешнюю задержку и работу приложения.

## Изменения этого релиза

- PDP больше не строит весь каталог из 643 товаров для восьми рекомендаций;
  используется отдельный `LIMIT 8` запрос.
- Медиа отзывов загружаются одним агрегирующим запросом вместо N+1.
- Публичный JSON кэшируется с singleflight, ETag и явной инвалидацией.
- Заглушка карточки уменьшена с 2,5 МБ PNG до 75 КБ WebP; исходный PNG пока
  сохранён.
- Новые S3-объекты получают годовой immutable cache. Миграция 075 безопасно
  ставит уже созданные зеркала в очередь повторной загрузки: рабочие URL не
  очищаются до успешного обновления метаданных.
- PDP резервирует размер основного блока skeleton-разметкой, чтобы загрузка
  данных и главного изображения не сдвигала весь экран.
