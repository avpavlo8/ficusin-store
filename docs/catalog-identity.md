# Идентичность товара и характеристики каталога

## Инварианты

1. Карточку растения и варианты размеров сначала создают на сайте. Сайт
   задаёт идентичность товара, его контент и розничную цену. Один вид и сорт
   с разными размерами горшка — одна карточка с несколькими вариантами.
   СБИС хранит складской остаток; его код вида `X...` — внешний артикул для
   сопоставления и складских документов, а не первичный ключ товара.
2. Внутренний идентификатор варианта — неизменяемый числовой SKU, например `123`.
   Его выдаёт PostgreSQL sequence, менять SKU после вставки запрещает trigger.
3. Числовые `products.id`/`product_variants.id` остаются ключами связей в БД.
   URL продолжает использовать стабильный `products.slug`. Поэтому миграция
   SKU не меняет ссылки, корзины и строки существующих заказов.
4. Saby, Wildberries, Ozon и любой следующий канал связываются с вариантом
   через `product_external_ids` и рабочие записи `procurement_product_channels`.
   Внешний ID никогда не генерирует Ficusin SKU.
5. Старые значения `product_variants.sku` не теряются: они записаны как
   `provider=ficusin, id_type=legacy_sku` до назначения нового SKU.
6. Пустое значение интеграции не удаляет подтверждённый mapping и не затирает
   локальный контент. Исправленный или снятый артикул получает статус
   `legacy`, продолжает связывать исторические продажи и исчезает только из
   списка текущих артикулов.
7. У одного SKU может быть несколько артикулов Ozon/WB. В Wildberries
   пользовательским идентификатором является `vendor_code`; числовой `nmID`
   хранится как скрытый технический ключ для входящих продаж и вызовов API.
8. Синхронизация СБИС не вправе менять локальную розничную цену. Новый
   артикул без подтверждённой связи с вариантом сайта ждёт сопоставления;
   он не публикуется как новая карточка автоматически.

## Цена и каналы

После расчёта инвойса порог изменения сравнивает предложенную розничную цену
с зафиксированной на тот момент ценой варианта **на сайте**. При превышении
настроенного порога появляются отдельные предложения для сайта, СБИС, Авито,
Wildberries и Ozon. Подтверждение одного канала не подтверждает остальные.
Изменение цены сайта или явной цены канала готовит ценовые draft в общем
редакторе. Отправка WB/Ozon/СБИС/Авито требует отдельного подтверждения владельцем;
старый source=manual в закупочной очереди удалён. Контракт и перенос истории —
`editor-price-publications.md`. Контентное обновление существующей карточки
не меняет её внешнюю цену; начальное создание включает начальную цену.
Общий редактор отправляет название и характеристики в СБИС через native
publisher после явного сохранения; создание и обновление
описаны в `site-saby-catalog.md`. Закупочные предложения цен СБИС по-прежнему
передаются подготовленным XLSX. Скачивание файла
и отметка об импорте не доказывают, что цена действительно изменилась в СБИС:
это нужно отдельно сверить. Цена на сайте от обратной синхронизации СБИС
не меняется.

## Атрибуты

- `attribute_definitions` описывает код, тип, единицу, варианты значения и
  аудиторию (`customer` или `technical`).
- `category_attributes` задаёт обязательность, фильтр, PDP, важную плашку и
  порядок для категории. Дочерняя категория наследует схему предка; ближайшее
  определение имеет приоритет.
- `product_attribute_values` хранит JSONB-значение и источник.
- `GET /api/v1/admin/categories/{id}/attributes` отдаёт эффективную схему для
  category-driven редактора.
- При создании опубликованной карточки, смене категории/характеристик и
  повторной публикации backend проверяет все `is_required`. Старые карточки
  не снимаются с витрины массово: правило начинает действовать при их
  содержательном редактировании.
- Публичные API отдают только customer-атрибуты. `is_filterable` строит
  фильтры каталога, `show_on_pdp` — таблицу характеристик, `is_badge` —
  короткие плашки. Technical-поля в клиентский контракт не попадают.

Числовые размеры SKU и упаковки хранятся в `variant_attribute_values`:
`height_cm`, `pot_diameter_cm`, `package_length_cm`, `package_width_cm`,
`package_height_cm`, `package_weight_grams`. Чтения используют
`variant_numeric_attribute`; сезонная упаковка — `shipping_package_dimension`.
Миграция 218 архивирует прежние шесть колонок варианта и массивы
`products.override_fields` / `product_variants.override_fields`, затем удаляет
их из рабочей схемы. Недостающие PIM-значения переносятся перед удалением;
существующие значения PIM не заменяются старой копией из колонки.
Архивы — `legacy_archive.product_retired_overrides` и
`legacy_archive.variant_retired_dimensions`, с исходными ID и временами.
«Недостающее» означает отсутствие строки атрибута: существующие JSON null,
ноль, отрицательное значение или числовая строка сохраняются вместе с source
и updated_at. Если для непустой старой колонки нет числового определения
уровня variant, миграция останавливается до удаления колонок.

Это не удаление всех typed-полей товара: редакционные классификаторы PRODUCT
и их мост в `product_attribute_values` пока участвуют в действующем API.
Не восстанавливайте удалённые поля как верхнеуровневые алиасы PATCH первого
SKU: существующие размеры редактируются через `variants` с явным ID.

## Фотографии

`product_media.object_key` может временно содержать URL поставщика.
`media_mirror` связывает его с собственными `card` (600 px) и `large`
(1200 px) копиями в S3. Все клиентские и административные чтения выбирают
собственную копию через `COALESCE`; после зеркалирования недоступность Saby не
влияет на изображение. Очередь запускается сразу после старта приложения,
повторяет временные ошибки и ограничивает размер входного файла.
Миграция `045_retry_external_photo_migration.sql` один раз возвращает в очередь
только используемые Saby-фотографии без готовой собственной копии; успешные
mapping и локальные изображения она не затрагивает.
Загрузчик принимает исходники и redirects только с HTTPS-доменов Saby — URL
из интеграции не может использовать приложение для запросов во внутреннюю
сеть. Сводка полного состояния галерей доступна владельцам каталога через
`GET /api/v1/admin/catalog/media-health`.

## Добавление интеграции

Добавляйте mapping транзакционно вместе со связыванием товара:

```sql
INSERT INTO product_external_ids(product_id,variant_id,provider,id_type,external_id)
VALUES ($1,$2,'marketplace','offer_id',$3)
ON CONFLICT(provider,id_type,external_id) DO UPDATE SET
  product_id=EXCLUDED.product_id, variant_id=EXCLUDED.variant_id,
  updated_at=CURRENT_TIMESTAMP;
```

Не добавляйте новый внешний ID колонкой в `products` и не используйте его в
заказах. Колонки `saby_id` пока участвуют в действующем обмене и связывании SKU:
`LinkVariantToSaby` обновляет связь варианта, склад читает её при синхронизации,
а `canonical_product_directory` согласует её с внешними ID. Это рабочее зеркало,
а не уже снятый read-only путь. Удаление требует отдельного перевода этих
читателей и писателей на канонические внешние ID.

В редакторе товара Ficusin/Saby mappings защищены от ручного удаления.
WB/Ozon/другие mappings меняются явно и транзакционно; конфликт внешнего ID
с другим товаром отклоняется, а не перепривязывает идентичность молча.

Saby sync сохраняет raw `attributes` в `saby_nomenclature.characteristics` и
переносит только allowlist известных кодов с корректным типом/enum. Пустой
supplier value ничего не стирает, а `source=local` всегда приоритетнее Saby.
