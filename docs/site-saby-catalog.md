# Карточка сайта → СБИС

Растения и варианты размеров создаются на сайте. В форме создания достаточно
названия, горшка, высоты и цены. Дробный диаметр сохраняется без округления.
Карточка остаётся скрытым черновиком с нулевым остатком.

В редакторе «Размеры и цены» владелец видит сохранённые данные и отдельную
кнопку «Создать в СБИС» / «Обновить в СБИС». Для существующей номенклатуры
можно выбрать «Связать SKU». Автоматического создания при открытии страницы,
сохранении черновика, импорте остатков или расчёте закупки нет.

Отправка доступна после сохранения карточки. Сервер сверяет fingerprint с
текущими данными, записывает долговечное задание и возвращает его состояние.
Цена передаётся в основной прайс только если она отличается от прочитанной
в СБИС. Налоги и остатки не меняются командой каталога. После подтверждения
создаются каноническая внешняя связь SKU, локальная запись справочника и
переходный saby_id. Остаток остаётся недоступным до настоящего складского обмена.
Публикация товара на сайте выполняется отдельно.

## Повторы и неизвестный результат

Одна запись `catalog_saby_exports` на SKU хранит постоянный код импорта,
снимок данных, ревизию, границу попытки POST, lease и уникальный claim token.
Параллельные нажатия не создают несколько команд. Повтор того же подтверждённого
набора данных не вызывает внешний POST. Для новой карточки постоянный код
записывается до обращения к СБИС и не зависит от названия/горшка.

Перед POST worker ещё раз сверяет сохранённую цену и характеристики сайта.
Перед самим сетевым запросом фиксирует attempted_at. После таймаута, 5xx,
неполного успешного ответа или перезапуска разрешено только чтение результата,
а не повторное создание. «Проверить результат» тоже выполняет только сверку.
Явная отрицательная ошибка JSON-RPC допускает новую отправку после исправления.

Состояния: idle → queued → checking → verifying → synced. Ошибка до отправки
или однозначный отказ дают error; неизвестный результат / длительная сверка
дают unknown. Из unknown нельзя молча создать новый товар или сменить данные
задания. Поля карточки сайта при этом можно редактировать, но новая отправка
ждёт разрешения предыдущей.

Совпадения названия недостаточно для автоматического связывания. Нужны точные
код и ID; найденная похожая карточка блокирует новое создание и предлагает
ручную связь. Пока команда выполняется, ручная перепривязка запрещена.
Отправленный/обрабатываемый SKU нельзя удалить с потерей его истории — можно
архивировать. Ограничение защищено также триггером БД для каскадного удаления.

## Проверка результата

Используется публичный `СБИС.ИмпортНоменклатурыИзCML`, protocol 3,
params.Параметр.Файл, Base64 XML UTF-16 LE с BOM и заголовком как в официальном
образце. В CML ровно один товар и режим «только изменения». Отсутствуют
складское количество и блок налогов. Денежные значения строятся из целых копеек.

`result:null` означает принятие запроса, а не подтверждение значений. Worker
читает каталог по полному и альтернативным фрагментам названия, фильтрует по
неизменному коду/ID и проверяет название, горшок, высоту и цену. Это учитывает
наблюдавшиеся в рабочем СБИС расхождения характеристик между поисковыми запросами.
Если значения не подтверждаются, сайт показывает ожидание/неизвестный результат,
не повторяет POST и не затирает локальные характеристики данными СБИС.

Существующие цены закупочных предложений и их XLSX-экспорт остаются отдельным
процессом; эта функция не подтверждает и не исполняет предложения WB/Ozon/Авито.
Она не создаёт карточки маркетплейсов. После приёмки можно сохранить уточнённые
габариты в редакторе размера и явно отправить их в СБИС этой же кнопкой.

## API и доступ

- GET /api/v1/admin/variants/{variantId}/saby-export — локальный предпросмотр и состояние.
- POST того же URL с fingerprint — поставить сохранённый снимок в очередь.
- POST с checkOnly:true — ускорить только чтение неизвестного результата.

Обе операции доступны только действующему владельцу панели. Сервисные ключи
берутся из существующего окружения SABY_APP_CLIENT_ID / SABY_APP_SECRET /
SABY_SECRET_KEY. Пустая конфигурация видна в интерфейсе и исключает отправку.
Команды и подтверждения попадают в admin_audit_log с инициатором.

## Проверки

Тесты проверяют потерянный ответ и рестарт без повторного POST, пропуск
неизменившейся цены, устаревший снимок, отсутствие связанной карточки,
параллельные нажатия на настоящем PostgreSQL, восстановление lease,
защиту от устаревшего claimant, каноническую связь, скрытый статус и запрет
удаления активной команды. Браузерные проверки покрывают создание с дробным
горшком, явную отправку, сверку unknown, отсутствие повторной отправки и
блокировку несохранённых изменений на компьютере, iPhone и Android.

Ручной live-тест Go-адаптера допускается только на отдельной probe-ветке с
фиксированным тестовым ID 3952 и известным кодом. Обычный CI его пропускает.
Тест проверяет изменение имени/высоты/цены и восстанавливает тестовые значения;
он не принимает произвольные ID или реальные растения.
