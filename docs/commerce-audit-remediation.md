# Исправления оплаты и возвратов, 22 октября 2026

## Реализовано в этом изменении

- Короткий номер заказа сохранён. Оплату открывает владелец аккаунта либо
  отдельный случайный ключ нового гостевого заказа. В БД хранится только хэш.
  Старые гости входят по телефону. Привязка к аккаунту отключает гостевой ключ.
- IP-лимит действует до проверки доступа; лимит заказа — после неё, чтобы
  перебором нельзя было исчерпать попытки оплаты чужого заказа. IPv6 объединяется
  по /64. Проверка звонка тоже ограничена с учётом трёхсекундного polling.
- Возврат — отдельное действие владельца. Правка состава не возвращает деньги.
  Поступления не переписываются в `refunded`: возвраты остаются отдельными фактами.
- Сохраняются инициатор, пользовательский ID запроса, все части возврата и точный
  запрос провайдеру до первого POST. Повтор того же запроса после успеха не создаёт
  ещё один возврат. Другой состав или сумма с тем же ID отклоняются.
- `pending` не считается успехом. Фоновый worker проверяет ID возврата через GET.
  При потерянном ответе повторяет исходный POST с тем же ключом только до 23 часов.
  После срока — ручная сверка владельцем по ID ЮKassa, без повторного списания.
  Неоднозначные исторические pending без сохранённого запроса также требуют сверки.
- Своя касса: после успеха остаётся отдельная задача по чеку возврата прихода.
  Кнопка подтверждает уже сформированный чек и сохраняет сотрудника; не печатает,
  не подписывает и не создаёт бухгалтерские документы.
- Чеки ЮKassa: полный возврат использует сохранённый состав исходного платежа.
  Частичный возврат без точного состава чека блокируется. Доработка такого сценария
  требует отдельных фискальных позиций, а не пропорционально придуманных товаров.
- Telegram отправляет существующий фоновый worker по сохранённому заказу.

Исторические записи `succeeded` не переоцениваются без данных ЮKassa. Это изменение
не доказывает правильность уже выполненных возвратов или наличие исторических чеков.

## Резерв в СБИС: ограничение API

23 октября в 08:33 профильный специалист поддержки ответил: «Резервирование
товаров в заказах через API в Saby не реализовано». Отдельного тестового контура
также нет. Это отменяет предположение из первого ответа о reserveTill и резерве
через Retail order. Автоматический резерв не включён. Ниже сохранён целевой
процесс владельца; для реализации нужен подтверждённый поддерживаемый способ.

Предложение владельца: резервировать в СБИС при заказе, отражать продажу при
фактической передаче СДЭК или выдаче самовывоза. Сейчас этот режим ещё не включён;
до реализации действует прежняя проверка свежего снимка без нового резерва.

Предлагаемая последовательность:

1. Сохранить заказ и задание обмена. Создать связанный заказ/счёт в СБИС с устойчивым
   внешним ID; повторный ответ и сетевой таймаут не должны порождать второй документ.
2. Подтвердить резерв точных SKU на нужном складе. Само наличие документа не означает,
   что свободного товара хватило: СБИС допускает резервирование при недостатке.
3. Открыть оплату только подтверждённой доступной части по действующим правилам;
   смешанный заказ не открывает частичную оплату сам. При недоступности СБИС заказ
   сохраняется без списания денег и передаётся менеджеру.
4. Владелец согласовал 22 октября 2026: неоплаченный онлайн-заказ с уже известной
   доставкой резервируется на **1 час**. Это решение для нового процесса, который
   ещё не включён. Начало срока фиксируется при подтверждении обеспеченного резерва
   и доступности оплаты; задержка обмена не должна съедать время покупателя.
   Заказы с расчётом менеджера и оплатой при выдаче требуют отдельного срока;
   автоматически применять к ним час нельзя. Перед освобождением сверить все
   попытки оплаты с ЮKassa. Оплаченный заказ, удержание денег и неизвестный результат
   платежа не освобождаются одним таймером. Срок в СБИС не должен истечь сам, пока
   идёт эта сверка: технический срок СБИС и клиентский срок оплаты — разные поля.
5. Оплаченный товар сохраняет резерв до передачи или отмены. Создание накладной СДЭК
   и регистрация отправления ещё не означают физическую передачу.
6. После подтверждённой передачи провести связанную реализацию на точные количества
   отправки. Для частичных отправок нельзя списывать весь родительский заказ.
7. При отмене до передачи снять резерв. Возврат денег — отдельная операция. После
   передачи деньги и физический возврат растения тоже учитываются раздельно;
   доступный остаток появляется после приёмки и проверки, с существующим процессом уценки.

Документация подтверждает возможности интерфейса СБИС; конкретный способ записи
и проверки резервов через доступный API/права аккаунта ещё требует проверки.
В текущей интеграции таких вызовов нет. Проверенные публичные контракты Retail
не описывают подтверждение обеспеченности резерва, его продление и связанную
реализацию по факту передачи. Это пробел проверки, а не доказательство отсутствия
этих возможностей в СБИС. Нужны поддерживаемые методы, примеры ответов и права
сервисного приложения; до этого автоматический складской режим не включать. Розничный API заказа и его платежные
операции нельзя включать вслепую: нужно исключить вторую оплату или фискализацию
параллельно существующей ЮKassa и кассе магазина.

Источники: [резерв СБИС](https://saby.ru/help/inventory/stock/reserve),
[отчёт по резервам](https://saby.ru/help/inventory/report/reservation_date),
[API заказов Retail](https://saby.ru/help/integration/api/app_sale/sale_delyvery/order_create).

## Дополнительные исправления, 23 октября 2026

- Вход по звонку требует случайный секрет браузера в HttpOnly-cookie на 5 минут;
  в БД хранится только хэш. Чужой браузер не вызывает проверку SMS.ru и не получает
  сессию даже при известном телефоне и checkId. После успеха проверка одноразовая.
  Уже открытые сессии остаются действительными; старую незавершённую проверку
  без привязки нужно запросить заново.
- GitHub OIDC дополнительно проверяет неизменяемые repository_id=1020342749 и
  repository_owner_id=77918099; значения сверены через GitHub API.
- Замена метатегов буквальная: `$1` и `${name}` в названии не становятся ссылками
  на группы регулярного выражения. HTML по-прежнему экранируется.
- Сравнение токена фида Авито использует хэши фиксированной длины и constant-time
  compare. Новые записи получают токен из криптографических UUID PostgreSQL.
  Существующий URL не ротирован: действующие подключения и ручные паузы сохранены.
- Публичная диагностика отдаёт только статус и версию. Коды внутренних проблем,
  количества и возраст задач доступны в защищённой панели. Внешний монитор
  продолжает различать ok/degraded/unavailable; workflow обновлён для этого ответа.
- GET-запросы расчёта и ПВЗ СДЭК вынесены до транзакции оформления. После них сервер
  заново читает цены, скидку, публикацию, упаковку и наличие. При изменении упаковки
  заказ сохраняется с ожиданием расчёта менеджером, без устаревшей стоимости доставки.

Проверки выполняются на отдельной локальной PostgreSQL с заглушками перевозчика и
телефонии. Реальные звонки, платежи, отправления и документы СБИС не создаются.

## Раздельное согласие и оферта

В оформлении две независимые обязательные отметки без предустановленного согласия.
API не трактует старый `consent=true` как принятие оферты; для нового заказа нужны
оба поля. Две отдельные записи с документами `personal_data_consent` и `offer`
сохраняются атомарно с заказом. При регистрации запрашивается только отдельное
согласие, принятие оферты относится к покупке. Опубликован отдельный текст согласия,
связанный с политикой; редакция подтверждений повышена до `2026-10-23.1`.
Исторические подтверждения остаются в первоначальном виде.

Основание разделения: [статья 5 закона №156-ФЗ от 24.06.2025](https://www.consultant.ru/document/cons_doc_LAW_508287/1500545af6526db1dfa11aba44d4df42208a0b05/).
Это исправляет объединение подтверждений в интерфейсе и журнале; не является
полной юридической проверкой всех оснований обработки данных магазина.

## Денежные расчёты: 23 октября

- Новый заказ суммирует цены после скидки по SKU в `int64` копейках; доставка
  прибавляется в копейках. API и PostgreSQL NUMERIC сохраняют рублёвый контракт,
  исторические суммы и уже сохранённые payload платежей/возвратов не переписываются.
- Платёжный баланс читает NUMERIC сразу как BIGINT копейки. Суммы оплаты должны
  совпадать точно; допуск в одну копейку удалён. Возврат с долями копейки отвергается
  до подготовки попытки. Провайдерские десятичные строки разбираются без ParseFloat;
  NaN, бесконечность, дробные копейки и суммы вне диапазона не принимаются.
- Чек проверяется на точную сумму позиций; ключи идемпотентности, очередь сверки,
  разделение удержания и оплаты, ручная проверка неизвестных операций сохраняются.
- Распределение закупочных расходов использует целые копейки и точные рациональные
  остатки. Курс, ставки и себестоимость единицы сохраняют доли копейки до итога:
  преждевременное округление поменяло бы экономику закупки. Ценовая формула и
  округление до целого рубля/50/90 сохраняются; устранена погрешность двоичных
  чисел на границе округления вверх. Это расчёт предложений, не публикация цен.
- Суммы корзины и результат оплаты в браузере также складываются в копейках.
- Проверено: полный Go suite с `-race` на изолированной БД, расчёты копейки,
  доплаты/частичного возврата, повторов, провайдерские payload, frontend build.


## Форматирование и OpenAPI: 23 октября

- Исходники Go приведены к gofmt, frontend — к закреплённой версии Prettier.
  Форматирование идёт отдельным коммитом; CI проверяет оба формата.
- OpenAPI покрывает все 241 зарегистрированные HTTP-операции, в том числе
  условно включённые chat/Avito и feed с отдельным server URL. Исправлены
  устаревший `/products/{code}` и повреждённые inline YAML descriptions.
- Контракты заказа, браузерной привязки входа, владельца/гостевого ключа оплаты,
  баланса и возвратов описаны отдельно. Денежный JSON остаётся в рублях с копейками.
- Проверка Go AST и OpenAPI 3.1 в CI запрещает пропуск новых маршрутов, устаревшие
  операции, неразрешимые ссылки, повторные operationId, потерю path-параметров,
  авторизации администратора и полей основных запросов.
- У части внутренних операций backoffice схема ответа пока не детализирована:
  наличие маршрута в спецификации не выдаётся за полное описание каждого payload.


## Доработка формул и мобильного UX, 23 октября

Оставшиеся старые формулы цены МП/зачёркнутой цены, округление розницы 50/90,
порог изменения цены и покрытие постоянных расходов используют точные
десятичные операции до итогового округления. В объединённой формуле целевой
вклад и себестоимость не преобразуются обратно в float между расчётом и ceil.
Пересчёт не публикует цены и не создаёт документы.

Дополнены проверки граничных округлений, процентной скидки на больших суммах,
переноса товаров в корзину. На телефоне закреплённая панель покупки показывает
название растения вместе с ценой; проверяются ширины 320/375/390 и отсутствие
перекрытия нижней навигации.

Последнее решение владельца: резервы и квоты каналов не включать. При нехватке
заказ отменяется, возврат оплаченного заказа выполняется отдельно. Действующие
правила обновлены в business-logic.md; будущая схема выше остаётся отложенной.
