# Чат сайта

Покупатель пишет сотруднику в быстром окне поверх любой страницы магазина, без обязательной регистрации. Все действия «Написать нам», «Написать в чат» и вопросы об уходе/заказе открывают это окно без перехода со страницы. История доступна прямо в быстром чате с постраничной загрузкой по кнопке «Предыдущие сообщения», а также в разделе «Сообщения» личного кабинета (`/account/chat`). Шапка быстрого чата содержит фирменную картинку магазина и кнопку сворачивания, без ссылки на кабинет. Старая ссылка `/chat` открывает быстрый чат. При сворачивании окна черновик сохраняется до перезагрузки страницы. Ссылки на социальные профили сохраняются как социальные ссылки.

Интерфейс переписки оформлен по просьбе владельца в стиле Telegram: голубые действия, светлый фон, белые и светло-зелёные сообщения, компактная шапка, время и галочки прочтения. Быстрое окно и кабинет используют одну серверную переписку. Полупрозрачная строка ввода содержит скрепку слева, поле сообщения, выбор смайлика и отправку справа; поле растёт с текстом. Скрепка принимает фото, видео и файлы. На мобильном быстрое окно является модальным: фон получает `inert`, Tab остаётся в окне, Escape закрывает его и фокус возвращается к прежнему элементу. На desktop окно немодальное. VisualViewport используется для подстройки окна при появлении клавиатуры. Каждое поле ввода имеет собственный ID, в том числе когда кабинет и быстрое окно смонтированы одновременно.

Сотрудники отвечают в `/admin?section=chat`. Право `chat.manage` доступно владельцу, администратору и менеджеру; роль проверяется сервером на каждом запросе. В меню виден общий счётчик непрочитанных сообщений. Входящие можно искать по имени, номеру обращения и тексту, фильтровать по открытым/решённым и просматривать страницами по 50. Решённое обращение открывается после нового сообщения. Отдельного обещания времени ответа или фиктивного статуса «онлайн» нет.

## Хранение и доступ

`support_conversations`, `support_messages`, `support_consents` находятся в PostgreSQL. История и байты вложений хранятся в базе, а не в файловой системе контейнера; их сохранность зависит от сохранности базы и её резервных копий. Гостевой доступ — 32 случайных байта в HttpOnly/Secure/SameSite=Lax cookie `ficusin_chat_session` сроком на год; база хранит только SHA-256. Просмотр окна создаёт cookie, но не пустую переписку. Только первое сообщение гостя требует отдельного согласия: версия политики `2026-10-22-chat`, время, IP и user agent записываются в `support_consents` в одной транзакции с первым сообщением. Для вошедшего покупателя используется согласие из регистрации, текст которого включает сообщения, фотографии, видео и файлы в чате; повторного чекбокса в чате нет, новая запись `support_consents` не создаётся. Сервер возвращает `consentRequired: true` только гостю без созданной переписки.

После входа история текущего браузера связывается с аккаунтом. Если у аккаунта уже есть чат, обе истории и свидетельства согласия объединяются. После выхода гостевая cookie не открывает историю аккаунта. На чужом устройстве без входа история недоступна. После удаления cookie неавторизованный посетитель теряет доступ. Учётная запись сохраняет доступ на других устройствах.

Сообщения и все вложения доступны только участнику и сотрудникам с `chat.manage`. По одному ID сообщения без доступа к переписке вложение недоступно. JPEG/PNG и распознанные по содержимому MP4/WebM выдаются inline; остальные файлы принудительно выдаются как `application/octet-stream` с `Content-Disposition: attachment`. Выдача вложений включает `X-Content-Type-Options: nosniff` и `Content-Security-Policy: default-src 'none'; sandbox`; `Range` обслуживается через `http.ServeContent` для частичной загрузки видео. Старые маршруты `/photos/` работают только для изображений. На API — `Cache-Control: no-store`, на HTML чата — `noindex`. Внешним мессенджерам ничего не отправляется. Оповещения — счётчики на сайте и в админке; фоновые push, SMS и email для чата не подключены. Содержимое переписки и cookie не пишутся в localStorage.

## Обмен и ограничения

Открытая видимая переписка обновляется каждые 4 секунды; входящие — каждые 5; счётчики — каждые 15. Скрытая вкладка или свёрнутое окно приостанавливают обновление переписки. При возвращении клиент загружает новые сообщения через `?after=<последний ID>`, последовательно по 50, пока не догонит историю: даже после более 50 ответов разрыва нет. Предыдущие страницы по 50 сообщений загружаются через `?before=<первый ID>` в быстром чате, кабинете и админке. Прочитанным считается входящее сообщение, нижняя часть которого реально видна одновременно внутри области сообщений и окна браузера. Скрытое окно или переписка ниже экрана не отправляют ложное прочтение. Курсоры ограничены существующими ID; будущие сообщения не могут оказаться заранее прочитанными.

Текст — до 4000 символов; на сообщение допускается одно вложение, в том числе без текста. Видео и файлы — до 20 МиБ (20 × 1024² байт); пустые вложения отклоняются. Для фото браузер сохраняет лимит исходника 20 МиБ, уменьшает длинную сторону до 1600 px, переводит в JPEG и удаляет EXIF. Сервер проверяет фактический формат JPEG/PNG, размер до 2 МиБ и до 16 млн пикселей. MP4/WebM определяются по содержимому, без обещания поддержки любого кодека браузером; нераспознанные видео и прочие форматы доступны как скачиваемые файлы. Имя вложения очищается до имени файла, ограничено 180 символами и не может содержать NUL/CR/LF. До 30 отправок сообщения и до 10 запросов с `attachment` в минуту с IP покупателя; лимит вложений применяется к попыткам после разбора JSON. Это лимиты одного экземпляра приложения, как у других публичных форм. При горизонтальном масштабировании лимитеры нужно вынести в общее хранилище.

Каждое сообщение имеет `clientId`; уникальность `(conversation_id,sender,client_id)` делает повтор после обрыва сети безопасным. При ошибке текст и вложение остаются в форме. Ctrl/Cmd+Enter отправляет сообщение; Enter добавляет строку. Вопрос из карточки, статьи или заказа добавляет ссылку на исходную страницу, которую покупатель может убрать перед отправкой.

## API

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/v1/chat` | Собственная переписка; `?before=<messageID>` для истории, `?after=<messageID>` для обновления |
| POST | `/api/v1/chat/messages` | `{clientId,text,attachment?:{name,data},consent?,contextUrl?,contextLabel?}`; `data` — base64 без префикса data URL |
| POST | `/api/v1/chat/read` | `{through:<последний видимый ID>}` |
| GET | `/api/v1/chat/unread` | `{unread:number}` |
| GET | `/api/v1/chat/attachments/{messageID}` | Приватное вложение; поддерживает `Range` |
| GET | `/api/v1/chat/photos/{messageID}` | Совместимый маршрут приватного JPEG/PNG |
| GET | `/api/v1/admin/chat` | `?status=open|closed&q=...&offset=0`; `{items,hasMore}` |
| GET | `/api/v1/admin/chat/unread` | Общий счётчик для сотрудника |
| GET | `/api/v1/admin/chat/{id}` | Переписка; `?before=...` для истории, `?after=...` для обновления |
| POST | `/api/v1/admin/chat/{id}/messages` | Ответ сотрудника в том же формате, согласие не требуется |
| POST | `/api/v1/admin/chat/{id}/read` | Прочтение сотрудником |
| PATCH | `/api/v1/admin/chat/{id}` | `{status:"open"|"closed"}` |
| GET | `/api/v1/admin/chat/{id}/attachments/{messageID}` | Приватное вложение для сотрудника; поддерживает `Range` |
| GET | `/api/v1/admin/chat/{id}/photos/{messageID}` | Совместимый маршрут приватного JPEG/PNG для сотрудника |

Ответ переписки: `{id,status,customerReadId,staffReadId,messages,hasMore,consentRequired}`. Сообщение: `{id,sender,text,contextUrl?,contextLabel?,hasImage,attachmentName?,attachmentKind?,attachmentSize?,createdAt}`; `attachmentKind` — `image`, `video` или `file`, `attachmentSize` — число байт. `hasImage` сохраняется для совместимости со старыми фото. Старое входное поле `image` (data URL JPEG/PNG до 2 МиБ после декодирования) остаётся совместимым, но не может передаваться вместе с `attachment`. Тело JSON ограничено 29 МиБ; base64 в `attachment.data` — 28 МиБ, декодированное вложение — 20 МиБ. Невалидные сообщения/отсутствие гостевого согласия дают 400, нет сессии сотрудника — 401, недостаточно прав — 403, чужое или отсутствующее вложение — 404, превышен лимит — 429, ошибка хранилища — 503. Частичный ответ вложения может иметь статус 206; неудовлетворимый `Range` — 416. Для больших загрузок (>3 МиБ JSON) и выдачи вложений приложение задаёт deadline 90 секунд; настройки reverse proxy проверяются отдельно.

## Проверки и выпуск

`go test ./...`, `go vet ./...`; PostgreSQL-тесты: `CHAT_TEST_DATABASE_URL=... go test -race ./internal/chat ./internal/httpapi -count=1`. Изолированные схемы удаляются после теста. CRM acceptance также запускает эти проверки в PostgreSQL.

`e2e/tests/chat.spec.ts` проверяет сбой/повтор, сохранение текста, контекст, ввод и переходы на desktop/iPhone/Android. `e2e/verify-chat-acceptance.mjs` проверяет настоящий Go + PostgreSQL в Chromium и WebKit: сообщения в обе стороны, фото/видео/файлы, приватность скачивания, `Range` видео, смайлики, отсутствие повторного согласия для аккаунта, прочтение, перезагрузку, изоляцию доступа, закрытие и повторное открытие, отсутствие переполнения. Используются только локальные/CI пользователи. Скрипт не предназначен для production.

Схема вводится миграциями `20261022_site_chat.sql` и `20261022_site_chat_attachments.sql` (поля имени и вида вложения в `support_messages`). Они должны быть применены до работы нового приложения. При откате приложения таблицы нужно сохранить, чтобы не потерять переписку; не удалять миграции из журнала и не переименовывать их. Возврат предыдущего приложения временно уберёт интерфейс, но оставит данные для повторного выпуска.

Описанные проверки — состав локальной/CI проверки, а не подтверждение текущего production. Применение миграций, резервные копии PostgreSQL, лимиты reverse proxy и работа на опубликованной версии требуют отдельной проверки выпуска.
