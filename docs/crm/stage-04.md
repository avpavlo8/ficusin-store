# CRM — этап 04: продажи, дедупликация, обзор и аналитика

## Границы

Этап выполнен поверх этапов 02–03. Он не вызывает внешние кабинеты из интерфейса и не меняет аналитику потребности в разделе «Закупки». Avito остаётся источником без данных до отдельного подключения. Существующая `procurement_sales_daily` сохранена как совместимый агрегат для закупок; источником аналитики стал журнал `sales_events`.

## Контракт события

Каждая строка хранит канал, `source_event_id`, исходный документ и строку, необязательный общий ключ источников, дату события, дату последнего импорта, товар источника, канонический SKU, тип события, подтверждённость, количество и сумму. Продажа, возврат, отмена и исправление различаются. Неоплаченный или ожидающий подтверждения заказ сохраняется для контроля, но в итоги не входит.

Повторное перекрывающееся окно обновляет событие по `(channel, source_event_id, source_line_id)`. Исчезнувшая из полного окна строка сохраняется в журнале как исключённая. Поздний возврат учитывается в дате возврата. Отмена до выкупа остаётся исключённым фактом и не создаёт отрицательную продажу.

События СБИС и маркетплейса объединяются только при одинаковом `cross_source_key` и каноническом SKU. Атрибуция остаётся у Ozon или Wildberries; СБИС без признака маркетплейса остаётся источником розницы. Совпадение суммы и времени не является основанием дедупликации. Два разных маркетплейса с одним ключом получают состояние «неоднозначно» и ждут сверки.

## Статусы источников

- Сайт: продажа — строка оплаченного или выполненного заказа; неоплаченный заказ — `pending`; отменённый — `cancellation`; успешный `payment_refunds` — возврат по дате проводки.
- Ozon: только отправление со статусом `delivered`; первичный документ — `posting_number`; строки — товары отправления.
- Wildberries: запись оперативного отчёта; `saleID` с префиксом `R` — возврат, остальные записи — продажи.
- СБИС: загрузка принимает устойчивые ID документа/строки, тип, статус и общий ключ. Старый формат поддержан как явно агрегированная строка дня.
- Avito: «Нет данных», сумма не подменяется нулём.

## Показатели

Период включает календарные сутки Москвы. Сравнение использует непосредственно предшествующий период той же длины. Выручка — подтверждённые продажи минус возвраты по дате события. Заказы — уникальные первичные документы продаж. Средний чек — подтверждённая положительная сумма до возвратов, делённая на число заказов. Проданные единицы — продажи минус возвращённые единицы.

Итоги каналов и товаров строятся из тех же учтённых событий, что общий итог. Повторы, несопоставленные, неоднозначные, ожидающие подтверждения и отменённые строки видны отдельно в блоке качества данных. Экран содержит переход к заказам и отдельную ссылку в закупки.

## Приёмка и ограничения

Live-тест PostgreSQL проверяет одну продажу из Ozon и СБИС, повтор окна, одинаковую сумму без общего ключа, поздний возврат, две единицы одного товара, неоплаченную строку, неподтверждённую связь, переход московских суток, отмену и пустое окно. API и Playwright проверяют сводные числа, очередь сверки, фильтр канала, Avito «Нет данных» и desktop/mobile раскладку.

Ручная сверка с первичными документами внешних кабинетов не выполняется в PR: тестовая среда намеренно запускается без production-ключей, а чтение реальных данных не требуется для изменения production. Перед выпуском фактические ID документов в очередной разрешённой выгрузке нужно сравнить с журналом событий. Следующий этап автоматически не начинать.
