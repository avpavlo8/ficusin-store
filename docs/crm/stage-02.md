## Реализовано

- PostgreSQL хранит отдельные дорожки `catalog` и `sales`: расписание текущего и глубокого прохода, поколения запроса, курсоры, границы периода, последнюю дату события, попытку, успех, ошибку, cooldown, владельца lease и fencing token.
- Текущий импорт продаж Saby/Ozon читает 30 дней каждые пять минут. Полная 365-дневная сверка выполняется раз в семь дней. Расписание глубокой сверки переживает перезапуск, поэтому новый процесс не начинает годовой импорт заново.
- Ручная кнопка только ставит задачу в БД. Повторные нажатия объединяются; нажатия во время активного снимка оставляют одно следующее поколение для недавно созданного товара.
- `CatalogWorker` один выполняет чтения Ozon/Saby. `SyncChannelCatalog` и `PrepareBatch` используют локальное зеркало. Для WB они читают существующее зеркало и не создают второй worker.
- Lease для всех дорожек и `ActionWorker` защищены владельцем и монотонным токеном. Завершение зависшего процесса после захвата задачи преемником игнорируется.
- Общий PostgreSQL limiter разделён по каналу, аккаунту и пути метода. Ожидание отменяется контекстом; HTTP 429 сохраняет `Retry-After` как общий cooldown аккаунта. Сбой или пауза WB не блокирует Ozon/Saby.
- Интерактивная работа получает приоритет в первые пять минут; затем возраст перестаёт удерживать фон, чтобы он не голодал.
- Страница владельца «Маркетплейсы» показывает `last_attempt`, `last_success`, границы, последнюю дату события, ошибку, cooldown и следующий глубокий проход. Ноль строк явно не трактуется как полнота. Продажи с последним событием старше 30 дней показываются устаревшими, включая прежнее состояние Saby «актуально» при последней продаже в 2025 году.

## Проверенные официальные источники

Проверено 12.09.2026:

- Wildberries: [финансовые отчёты и бухгалтерия](https://dev.wildberries.ru/docs/openapi/financial-reports-and-accounting) и [release note от 15.04.2026](https://dev.wildberries.ru/en/release-notes?id=354). Новый детальный отчёт использует `POST /api/finance/v1/sales-reports/detailed`; для новых финансовых методов указан лимит один запрос в минуту на аккаунт. Старый `GET /api/v5/supplier/reportDetailByPeriod` объявлен к отключению 15.07.2026. Этот этап сохраняет действующее оперативное зеркало `/api/v1/supplier/sales`; финансовый импорт новым методом не подменяет.
- Saby: [официальная справка API](https://saby.ru/help/integration/api) подтверждает online API и выгрузку/актуализацию номенклатуры Saby Retail. Числовой общий лимит для используемых методов в доступной официальной справке не найден, поэтому код не утверждает фиксированную квоту: применяет консервативный темп и `Retry-After` сервера.
- Официальная Seller API страница Ozon `https://docs.ozon.ru/api/seller/` на дату проверки зацикливала перенаправление и не дала подтвердить числовую квоту. Поэтому значение квоты не считается контрактом: используются раздельные method/account gates, консервативный темп и фактический `Retry-After`.

## Приёмка, откат и handoff

Владелец открывает «Маркетплейсы», ставит обновление Ozon/Saby и видит очередь без синхронного сетевого ожидания. Повторные нажатия не увеличивают число проходов; после результата видны попытка, успех, период, событие и следующий запуск. Менеджер получает 403 на прямой URL и API закупок. Перед production выпуском отдельно проверить один разрешённый аккаунт каждого канала и сверить число/границы строк с кабинетом.

Откат кода — revert коммита. Добавленные таблицы и колонки можно оставить: старый код их игнорирует, история и курсоры сохраняются. Удалять их при оперативном откате нельзя, чтобы не потерять состояние задач. Для полного удаления после выгрузки данных: остановить workers, удалить новые колонки `procurement_action_items` и `procurement_wb_sync_state`, затем таблицы `procurement_integration_rate_limits` и `procurement_integration_sync_state`.

Следующим этапам использовать `IntegrationSyncCoordinator`, локальные `procurement_channel_products`/`procurement_channel_sales` и существующий `ActionWorker`. Не выполнять внешний read из HTTP handler и не считать `rows_synced=0` доказательством полноты. Новая миграция: `20260912_integration_sync_coordination.sql`. Несовместимость: реализации тестовых Store должны принимать owner/token в `ClaimAction`, `FinishAction`, `ClaimWBSync`, `FinishWBSync`.
