# Ревизия бизнес-правил перед наполнением каталога — 9 октября 2026

Статус: аудит кода `main` после релиза `8604bd9`. Владелец подтвердил правила для цен каналов и ручного завершения заказа; реализация этих ограничений идёт отдельно. Это проверка реализации, а не подтверждение каждой ветки реальным заказом.

## Согласованная основа, которая уже работает

- Карточка, варианты и розничная цена принадлежат сайту; складской остаток приходит из СБИС. Разные размеры одного вида и сорта — варианты одной карточки. Импорт СБИС не публикует несвязанный товар автоматически.
- Закупка сравнивает предложенную цену с сохранённой ценой сайта; порог хранится в настройках (исходное значение 10%). Сайт, СБИС, Авито, WB и Ozon подтверждаются отдельными действиями. Ручная правка цены сайта тоже создаёт предложения каналам.
- Для оплаты и создания обычного заказа требуется свежий (до двух часов) остаток СБИС по основному складу. При нехватке хотя бы одного растения оформляется один заказ без онлайн-платежа. Новые заказы не резервируют остаток. Перед открытием оплаты и созданием новой посылки остаток проверяется снова.
- Новые заказы принимают самовывоз и СДЭК. Покупатель платит тариф СДЭК на сайте вместе с растениями; СДЭК не собирает его с получателя. При неизвестном тарифе заказ сохраняется для решения менеджера без онлайн-платежа.
- Финансы доступны только владельцу по серверным правам. Возвраты пока остаются до проверки процесса. Автоматическое создание отправлений СДЭК выключено по умолчанию.

## Расхождения, которые нужно закрыть до наполнения каталога

### 1. Публикация цены канала раньше цены сайта — высокий приоритет

В закупке для СБИС, WB и Ozon можно подтвердить цену из инвойса, пока соответствующая цена сайта ещё старая. При утверждении партии проверка актуальности исходной цены действует для канала `site`, но не блокирует остальные каналы (`backend/internal/procurement/postgres_actions.go`, `frontend/src/AdminProcurementDialogs.tsx`). Это нарушает правило, по которому сайт хранит текущую цену, от которой расходятся каналы. Владелец подтвердил ограничение: внешние кнопки становятся доступны после утверждения цены сайта для того же расчёта; каждое направление по-прежнему подтверждается отдельно. Повторное изменение цены должно сделать старое предложение недействительным.

### 2. Ручные статусы заказа обходят проверки — высокий приоритет

`UpdateOrderStatus` в `backend/internal/admin/manage.go` позволяет сотруднику с `orders.edit` менять статус заказа и статус оплаты без проверки факта платежа, свежего остатка или допустимого перехода. Менеджерское редактирование состава (`backend/internal/admin/order_adjustments.go`) определяет нехватку по сумме всех складов, без двухчасовой свежести СБИС; так заказ может преждевременно выглядеть готовым. Платёжный API всё равно повторно проверяет наличие, но ошибочный статус может повлиять на ручное исполнение. Владелец подтвердил правило: перевод в «готов» или «завершён» требует свежего остатка и подтверждённой оплаты; при самовывозе с оплатой при получении менеджер отмечает фактическую оплату при выдаче. Ограничение должно проверяться на сервере.

### 3. Оформление товара «под заказ» требует лишнего выбора — средний приоритет

Покупателю показывают этап «Оплата» и способ «Оплата сразу после оформления» даже тогда, когда позиция недоступна и платёж не будет открыт (`frontend/src/CartCheckout.tsx`, `backend/internal/payment/payment.go`). Заказ без оплаты сейчас зависит от загрузки вариантов платежа. Стоит сохранить один обычный заказ, но показывать понятное объяснение «менеджер уточнит поставку; сейчас платить не нужно» и не требовать выбора способа оплаты для такого заказа. Контакты и способ получения остаются нужны менеджеру.

### 4. Остатки старой доставки — низкий приоритет

SEO-описание `/delivery-and-returns` исправлено ранее. В блоке оформления удалены неиспользуемые настройки фиксированных тарифов курьера и Почты России и публичный `/api/v1/delivery/fees`: среди кода сайта, приложения и проверок потребителей не найдено. Исторические названия способов в старых заказах сохранены. Внешние потребители публичного API не подтверждены; после выпуска старый адрес будет возвращать 404.

### 5. Внешние каналы ещё требуют сопоставления — блокер массовой отправки цен

Снимок админки в `docs/live-channel-links-2026-10-09.md` показывает 88 из 89 объявлений Авито без связи, а первая страница зеркала СБИС содержит множество несопоставленных позиций WB/Ozon. СБИС получает цену через подготовленный XLSX и ручной импорт; файл и отметка об импорте сами по себе не подтверждают цену в СБИС. Массовую отправку по Авито до очистки объявлений и проверки связей не включать.

## Порядок работы

1. Внедрить два подтверждённых правила: цена сайта перед отправкой цены каналам; ограничения ручного завершения и оплаты заказа при самовывозе.
2. Исправить проверку цены и ручные переходы заказа; проверить сценарии устаревшего СБИС, смешанного заказа, поздней оплаты и повторной цены. Выпустить небольшими PR, проверить точную версию на сайте.
3. Упростить оформление заказа без оплаты, сохранив общий путь заказа и обязательное согласие на обработку данных.
4. Очистить старое описание доставки и после проверки потребителей решить судьбу справочного API старых тарифов.
5. Проверить несколько реальных SKU и фактические цены в СБИС/WB/Ozon. Авито подключать после очистки и сопоставления объявлений.
6. После этого получить выгрузку владельца: сверить ассортимент, категории, карточки и контент. Размер горшка, высоту и фотографии заполняет владелец.
