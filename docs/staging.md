# Стейджинг

Изменения сначала проверяются на отдельном приложении Timeweb из ветки
`staging`, затем тот же коммит проходит PR в `main`. Слияние в `main` по-прежнему
автоматически выпускает рабочий сайт. Копирование тестовой базы в рабочую
не является выпуском и не допускается.

Окружение: `APP_ENV=staging`, собственный HTTPS `SITE_URL`, отдельная база
`ficusin_staging_20261031` и отдельный пользователь только для этой базы.
Размещается в уже существующем кластере; общих таблиц, клиентов, заказов,
сессий, очередей и миграций с production нет. Запуск отказывается работать
на базе с другим именем до миграций и фоновых заданий.

Timeweb App: `280757`, тариф `2731` (1 CPU, 1 ГБ RAM, 510 ₽/месяц).
Адрес: `https://avpavlo8-ficusin-store-1b1b.twc1.net`. База `564565` находится
в существующем кластере `4192781`; отдельный оплачиваемый кластер не создаётся.
Пользователь: `ficusin_stage_20261031`, без прав администрирования кластера.
Пул стейджинга ограничен тремя соединениями; production сохраняет свой лимит.
Поле Timeweb `health_check` должно оставаться пустым: непустое значение
добавляет проверку контейнера, которая зависает и откатывает готовое приложение.
Вместо неё готовность и точную версию проверяет внешний workflow.

API управления пользователями Timeweb пересчитывает права существующих ролей.
При первом создании тестового пользователя он снял права рабочего владельца
с его собственных таблиц. Доступ восстановлен, права `gen_user` закреплены
явно для `default_db`. Не создавать пользователя заново при обычных обновлениях
стейджинга. После операций с ролями недостаточно health/ready: нужно проверять
чтение рабочего каталога, карточек и доступ владельца к своим таблицам.

Стейджинг закрыт отдельным входом: логин `staging`, пароль из
`STAGING_ACCESS_TOKEN` (минимум 32 символа). Успешный вход сохраняется на
7 дней в подписанной Secure/HttpOnly cookie. Системных HTTP Basic запросов
браузер не получает: они конфликтовали с обычными ответами 401 аккаунта.
Явный Basic-заголовок поддерживается только для старых API-проверок.
Без входа доступны health/ready и запрещающий robots.txt. Закрытый доступ
обязателен: SMS-шлюз в этом окружении имитирует подтверждение звонка.
Для повторяемых проверок лимит тестового подтверждения увеличен до 100
запросов за 10 минут; рабочий лимит 5 запросов не меняется.
Секрет хранится в env нового приложения и Actions Secrets. Обычный вход
в аккаунт выполняется отдельно; рабочий профиль владельца перенесён без
пароля, заказов и списка клиентов. Браузерные проверки создают свежие
сессии через обычный вход, а не зависят от заранее подготовленного токена.

Для нового редактора на staging явно задаются `CATALOG_PUBLICATION_MODE=mock`,
`CATALOG_PUBLICATION_LIVE_ENABLED=false` и `FILE_STORAGE_MODE=mock`.
Категории и разделы СБИС в этом режиме имеют подпись «Тест СБИС»; они не являются
живыми справочниками аккаунта. Очередь WB/Ozon также использует тестовый провайдер.
Фото товаров/вариантов/подборок сохраняются в отдельной public mock-таблице,
а аватары, файлы чата, возвратов, отзывов и закупок — в отдельной private
mock-таблице изолированной staging-базы. Они переживают перезапуск контейнера.
Публичный маршрут изображений закрыт общим входом staging и не читает private
объекты. Production запрещает этот режим; `LOCAL_PRIVATE_FILES_DIR` на staging
не задаётся. Подробности — `docs/file-object-storage.md`.

В staging ключи внешних систем обнуляются конфигурацией независимо от env.
Он не отправляет товары, цены, заказы, платежи, доставку, письма и push во
внешние системы. На стейджинге экспорт новых карточек работает через явно обозначенный
тестовый провайдер без сетевых запросов: очередь, сохранение связи, цена,
горшок, высота и повторная отправка проходят полный внутренний цикл.
Тестовые идентификаторы начинаются с `STG-`; рабочие связи он отвергает.
Состояние хранится только в отдельной БД стейджинга. Это проверка механизма,
а не подтверждение отправки в настоящий СБИС.
Контрактные проверки настоящего СБИС выполняются отдельно с жёсткой
привязкой к синтетической карточке. Клиентские данные и рабочие сессии сюда
не переносятся. Каталог можно заполнить публичными данными или тестовыми
позициями; это не даёт прав на рабочий каталог СБИС.

На HTTP-ответах есть `X-Ficusin-Environment: staging`, запрет индексации,
robots.txt запрещает обход. Это технические признаки, а не замена авторизации:
доступ к административным данным требует обычную сессию владельца.

После первого запуска задаётся переменная GitHub `STAGING_BASE_URL`.
`Staging verification` строит эталон тем же Docker-этапом, ждёт точную версию
backend и побайтовое совпадение JS/CSS, проверяет изоляцию, непустой каталог
и выполняет браузерные проверки компьютера/iPhone/Android. GitHub environment
`staging` хранит результат для проверенного SHA.
Проверка PR требует и успешный deployment, и успешный запуск именно workflow
`staging-verification.yml` для того же SHA. Одной отметки окружения недостаточно.

Браузерная проверка витрины, проверка редактора и вход staging используют один
валидатор адреса: HTTPS origin `*.twc1.net` либо точный `staging.ficusin.ru`.
Адреса production, реквизиты в URL, custom port, путь, query и fragment
не допускаются при передаче staging-ключа. Проверка этого ограничения выполняется
локальным Node-тестом без запросов к этим адресам.

Порядок выпуска: зелёный CI → отправить коммит в `staging` → дождаться
успешного `Staging verification` и проверить изменённый сценарий → PR того
же коммита в `main` → проверка точной production-версии после слияния.
При исправлении кандидата проверка начинается заново для нового SHA.

Статус развёртывания и доступный адрес фиксируются после фактического запуска;
наличие ветки/конфигурации само по себе не означает готовое приложение.

## Проверка загрузки файлов

Для полного сценария редактора/чата/аватаров/возвратов/накладных без внешних
S3 writes задаётся **явный** `FILE_STORAGE_MODE=mock`. Этот тестовый провайдер
разрешён только в staging и дополнительно проверяет фактическое имя отдельной
БД. Две отдельные таблицы хранят тестовые private files и public product images;
последние доступны только через защищённый staging gate endpoint
`/api/v1/staging/media/{key}`, с ключами `products/`/`collections/`. Private
объекты не имеют public URL. Это позволяет проверять сохранение и перезагрузку
после деплоя, не используя рабочие S3 credentials и не теряя файлы контейнера.
На production режим `mock` запрещён, по умолчанию требуется настоящий private
S3. `LOCAL_PRIVATE_FILES_DIR` остаётся исключительно локальным dev-эмулятором и
на staging не используется. Подробнее: `docs/file-object-storage.md`.
