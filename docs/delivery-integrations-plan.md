# Интеграции доставки: проверенный план

Актуально на 16 августа 2026 года. Этот документ опирается только на
официальную документацию. Наличие API в документации не означает, что оно
подключено в договоре «Фикусина»: production-интеграция считается рабочей
только после успешного запроса с боевыми учётными данными.

## Почта России

Подходящий продукт — кабинет бизнес-отправителя
[«Отправка»](https://otpravka.pochta.ru/). Официальные
[обзор API](https://www.pochta.ru/support/business/api) и
[спецификация](https://otpravka.pochta.ru/specification) описывают расчёт
стоимости и сроков, нормализацию адреса, создание/изменение/удаление заказа,
партии, документы и получение ШПИ (трек-номера).

До реализации нужны: действующий договор, токен приложения, ключ пользователя,
индекс и данные точки сдачи, доступные договорные виды и категории РПО. Пока
они не проверены, checkout оставляет стоимость на подтверждение менеджеру и
показывает: «Оплата после подтверждения заказа менеджером».

План реализации:

1. Серверный `PostAdapter`: нормализация адреса, расчёт по индексу, весу,
   габаритам, виду РПО, объявленной ценности и допустимому наложенному платежу.
2. Сохранять quote, тариф, итоговую стоимость и срок действия расчёта.
3. Создавать заказ с постоянным внешним идентификатором Ficusin; перед повтором
   искать его по этому идентификатору.
4. После подтверждения менеджером добавлять отправление в партию и получать
   ШПИ; сохранять provider id, ШПИ, сырой и внутренний статус.
5. Использовать надёжный polling. В открытых официальных материалах не найдено
   подтверждение webhook со схемой проверки подписи, поэтому выдумывать такой
   endpoint нельзя.
6. Повторять только timeout, `429` и `5xx` с backoff и jitter. `4xx` писать в
   журнал ошибок для менеджера. Секреты и персональные данные не логировать.

## Яндекс Доставка

Официальная [точка входа API](https://yandex.ru/support/delivery-profile/ru/api/)
разделяет два B2B-продукта:

- [Экспресс-доставка](https://yandex.ru/support/delivery-profile/ru/api/express/quickstart)
  для срочных городских заказов;
- [Доставка по России](https://yandex.ru/support/delivery-profile/ru/api/other-day/)
  для плановой курьерской доставки, ПВЗ и постаматов.

«Яндекс Go» — не название универсального ecommerce API. Для Рязани договор,
географию, тип забора, склад/`platform_station_id`, доступность ПВЗ и оплаты при
получении необходимо подтвердить в бизнес-кабинете и реальным API-запросом.

Архитектура:

1. `YandexAdapter` с режимами `express` и `russia`, Bearer token только на
   сервере; feature flag выключен до проверки договора.
2. Quote хранит offer id, service/tariff, station/PVZ, цену, срок и expiry.
3. Express: `offers/calculate` → `claims/create` → `claims/info` →
   `claims/accept`; отмена через `claims/cancel-info` и `claims/cancel`.
4. По России: pricing/location/PVZ → offer create/confirm → request create;
   затем info/history, labels, handover и cancel согласно
   [официальному справочнику методов](https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/).
5. Для каждого create использовать уникальный устойчивый
   `operator_request_id`, локальную уникальность `(provider, order_id)` и
   transactional outbox.
6. Отслеживать info/history polling-задачей с дедупликацией события. Общая
   официальная схема webhook-подписи в изученных разделах не подтверждена.
7. Оплату при получении включать только если конкретный оффер/ПВЗ разрешает её;
   [официальные ошибки](https://yandex.ru/support/delivery-profile/ru/api/other-day/errors)
   прямо предусматривают недоступность такого способа.

## Production-проверка

Для каждого подключённого провайдера допустим один помеченный тестовый заказ:
quote → create → info/status → безопасная отмена до передачи перевозчику.
Сохраняются очищенные request id, HTTP status и время. Реальные отправления и
работоспособность нельзя заявлять без этого сценария.
