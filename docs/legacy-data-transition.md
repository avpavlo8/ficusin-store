# Перенос оставшихся исторических данных

Изменения подготовлены в отдельной рабочей ветке 14 ноября 2026. По отдельному
разрешению начата выкладка на изолированный staging; production не изменялся.
Исторические миграции не переписывались.

## Фактическая инвентаризация

Рабочая БД прочитана в транзакции `READ ONLY` с проверкой приложения, имени БД
и точного production-коммита. [Инвентаризация 43594244971](https://github.com/avpavlo8/ficusin-store/actions/runs/43594244971)
подтвердила:

- 0 файлов с исходными байтами без объектного ключа; 0 публичных объектов отзывов;
- 0 локальных резервов заказа и складов, 0 распределений shipment offer;
- 0 записей прежнего экспортера СБИС;
- 1 редактируемый план, уже с отдельными артикулами площадок;
- 2 незавершённых публикации: СБИС `needs_attention`, WB `failed`.

[Проверка объектов 43594655450](https://github.com/avpavlo8/ficusin-store/actions/runs/43594655450)
выполнила только подписанные S3 GET: 9 объектов читаются, у 8 есть сохранённый
источник и совпал SHA-256; у одного нового вложения исходных байтов в БД нет.
Среди проверенных: 1 аватар, 3 вложения чата и 5 документов закупок.
Ни один объект не записан и не удалён. Поле старого отчёта
`storage.objectsReadOrWritten=0` относится к первоначальной проверке конфигурации
и ошибочно осталось после добавления GET; действительные чтения отражены в
`objectVerification`, а последующий скрипт разделяет счётчики чтений и записей.

Это срез рабочего окружения, не разрешение обходить повторные проверки перед
будущей выкладкой. Черновики на ещё не посещённых клиентских устройствах
серверная инвентаризация не видит.

## Файлы: копия, проверка, архив

`backend/cmd/migrate-file-assets` по умолчанию составляет план переноса пяти
источников `bytea`. `--apply` сохраняет объект, читает его назад, сравнивает
SHA-256 и атомарно меняет ссылку вместе с записью
`file_asset_migration_history`. Исходные байты остаются на месте.
`--public-reviews` отдельно переносит уже имеющие ключи публичные объекты
отзывов: читает текущий объект, сохраняет проверенную приватную копию, условно
меняет ключ и `storage_scope`, сохраняет исходный ключ в журнале. Старый объект
не удаляется. Ошибка подтверждения транзакции не удаляет потенциально уже
используемую новую копию.

Перед выводом старого чтения нужен успешный полный запуск:

```sh
go run ./cmd/migrate-file-assets --verify --limit 10000
```

Команда выполняет только GET и SQL SELECT. Неполная выборка, недоступный объект,
несовпадение суммы, смена ссылки во время чтения или оставшийся старый источник
дают `ready=false` и ненулевой exit status. Контрольная сумма берётся из журнала,
сохранённых байтов либо архива; файл без старой копии помечается отдельно.
Проверяются реальные приватные настройки окружения, а не публичные URL.

Миграция `20261114_zzzzz_private_file_cutover.sql` блокирует изменения источников,
останавливается при любом неперенесённом файле/публичном отзыве, затем переносит
байты и полные исходные метаданные в отделённую
`legacy_archive.file_binary_payloads`. До очистки рабочих байтов проверяет
побайтовое равенство и SHA-256 SQL-копии. Новые CHECK запрещают возвращение
`bytea` и публичных отзывов. Нулевые колонки пока сохраняются для совместимого
перезапуска и автономного инструмента переноса.

Рабочие API аватаров, чата, возвратов/уценки, документов закупок и отзывов
используют только приватный S3; старое чтение БД и адаптер публичного бакета
удалены. Авторизация и маршруты не менялись. Публичные фото товаров используют
своё действующее хранилище и этим переносом не затрагиваются.

## Черновики и планы

Браузерный журнал теперь `version:2` под прежними ключами. Перед преобразованием
сохраняется точная исходная строка в неизменяемый
`${storageKey}:migration-backup:v1[:N]`. Варианты, выбранная вкладка, серверные ID,
артикулы, режим цен, связь СБИС и файлы сохраняются. Ошибка формата/квоты блокирует
небезопасную перезапись и публикацию, а исходник остаётся доступен.

В IndexedDB прежние Blob преобразуются в бинарные записи вместе с бинарной
резервной копией в одной транзакции. Нельзя архивировать старый Blob прямой
записью Blob: WebKit может её отклонить. База и object store остаются прежними.
Импортёр V1 сохранён для браузеров, которые ещё не открывали новую версию;
удаление по серверному счётчику потеряло бы их работу.

Редактируемые серверные планы нормализуются отдельной миграцией с исходным JSON
и контрольными суммами в `catalog_plan_format_history`. История прежнего
экспортера переносится в неизменяемый `catalog_external_operation_history`;
защита удаления использует его. Запросы уже начатых операций, fingerprints,
внешние ID и pending revisions не переписываются.
[Подробный контракт](catalog-compatibility-migration.md).

## Резервы и незавершённые операции

Нулевая рабочая инвентаризация позволяет снять старую цепочку локального
освобождения резервов. Миграция повторно проверяет нули под блокировкой,
архивирует исходные идентификаторы, количества и release timestamps с NULL,
запрещает старые записи. Физические остатки, текущие реализации СБИС и FIFO
не изменяются. При ненулевом резерве миграция остановится;
[ручной локальный инструмент сверки](legacy-reservation-reconciliation.md)
проверен на исторических фикстурах, но не запускается автоматически.

Неизвестные результаты внешних операций нельзя закрыть переносом JSON либо
сбросом receipt. По ним выполняется отдельное чтение площадки. Обнаруженная
карточка WB уже подтверждена точным артикулом и сохранённым штрихкодом;
автоматический повтор создания не выполнялся.

[Сверка площадок 43595841742](https://github.com/avpavlo8/ficusin-store/actions/runs/43595841742)
подтвердила принадлежность WB-карточки, включая первый штрихкод, который читает
текущий provider. Повтор публикации сможет подхватить существующую карточку,
но затем отправит фото и цену, поэтому в рамках read-only проверки он не
запускался. СБИС подтвердил точные ID/UUID и совпадение названия, категории и
раздела. При этом карточка осталась draft; описание, штрихкод, изображения и
инициализированная цена не подтверждены. Receipt использует старые prepared
hashes, есть pending revision. Требуется явная подготовка нового запроса к
существующей карточке; подмена хешей/сброс receipt не выполнялись.

Та же сверка подтвердила включённую единую модель цен. Настройки не менялись;
альтернативный расчёт пока остаётся разрешённым API, поэтому его удаление
потребовало бы отдельного изменения поддерживаемых конфигураций.

Пять августовских тестовых платежей и семь исторических заказов без финального
фискального документа не исправляются изменением финансовых фактов. Тестовый
когортный фильтр подготовлен ранее. Для исторических реальных чеков требуется
подтверждённый фискальный сценарий; этот перенос не создаёт чеков, новых оплат,
возвратов или списаний. Реальный `pending` и неизвестное создание оплаты нельзя
считать отменёнными по одному локальному статусу.

## Локальные проверки

- Полная чистая установка: 235 миграций; копия прежней полностью мигрированной
  базы обновилась с 230 до 235.
- Перенос файлов проверен на реальной PostgreSQL с fake object stores: точные
  байты/метаданные/старый ключ, повтор, конфликт ссылки, испорченная копия,
  отказ журнала, незавершённая выборка и чтение digest из архива. Исходные
  объекты и данные при отказах сохраняются.
- Каталог: старые null/empty/auto/manual планы, исходный JSON, неизменность
  frozen/pending requests и защита удаления по новому журналу.
- Резервы: конкурентный локальный pilot, точная принадлежность, fingerprint,
  неопределённые платежи/перевозчик, отказ ненулевого cutover, архив исходных
  NULL/timestamps и запрет старых producers.
- Frontend: 105 unit, 13 финальных browser cases на desktop/iPhone/Android,
  18 остальных compatibility cases; build, lint, формат, bundle budgets.
- Go: полный test/vet/build, 11 пакетов с PostgreSQL и race detector; OpenAPI
  241/241 операции и 94 схемы.

Тесты не заменяют повторную инвентаризацию и полный S3 verify перед будущей
выкладкой. Продолжение публикаций/фискальные действия этим коммитом не
разрешается и не запускается автоматически инструментами переноса.

При полной staging-проверке CRM-фикстуры переведены на приватные объектные
ссылки и нулевые локальные резервы. Проверка минимальной цены общего объявления
Avito теперь использует `order_sale_inventory`, как текущая витрина объявления:
FIFO-удержание заказа исключает недоступный размер из минимума. Регрессия
создаёт удержание реализации при неизменном физическом остатке, вместо записи
в снятый локальный счётчик.

Перед production CodeQL-замечания закрываются в исходниках: URL-фильтры каталога
читаются в словари без прототипа, а ошибка платёжного webhook логируется по типу
и SHA-256 идентификатора без сырых входных полей. Регрессии проверяют специальные
имена свойств, отсутствие наследования и сохранение поведения provider recheck/retry.
